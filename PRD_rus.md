# Tengu Cluster — Документ требований к продукту

> Модель-агностичный, адаптивный к оборудованию хаб AI-агентов. Единый бинарник, ноль зависимостей.

Этот документ содержит и текущее поведение, и целевое состояние.

## Как использовать Tengu Cluster

### Быстрый старт

```bash
# Сборка проекта
cargo build --release

# Запуск интерактивного чата (используется Ollama по умолчанию)
./target/release/tengu-cluster

# Или явно указать подкоманду
./target/release/tengu-cluster chat

# Проверить статус системы
./target/release/tengu-cluster status

# Диагностика проблем
./target/release/tengu-cluster doctor
```

### Требования

- **Rust** (для сборки): `rustup` + `cargo`
- **Ollama** (для Phase 1): запущенный локально на `http://localhost:11434`

### Конфигурация

Скопируйте пример конфигурации:

```bash
mkdir -p ~/.tengu
cp config.example.toml ~/.tengu/config.toml
```

Отредактируйте `~/.tengu/config.toml` под свои нужды:

```toml
# Выбор движка (engine) и модели
[agents.main]
engine = "ollama"
model = "llama3.2"              # любая модель из вашего Ollama
workspace = "~/projects/my-app" # рабочая директория агента

# Оптимизация токенов (по умолчанию выключена)
[refiner]
mode = "off"     # "off" — без оптимизации
                 # "rules" — регулярные выражения, 20-40% экономия
                 # "local" — ML-модель через Candle, 60-70% экономия
                 # "remote" — делегировать на другую машину
```

### Команды в чате

Во время разговора с агентом доступны следующие команды:

| Команда | Описание |
|---------|----------|
| `/eco` | Режим «эко» — только краткие версии файлов |
| `/standard` | Стандартный режим — краткая версия, разворачивается при необходимости |
| `/precise` | Точный режим — полное содержимое файлов всегда |
| `/engine` | Показать текущий движок и модель |
| `/cost` | Статистика использования токенов и экономия |
| `/context` | Использование контекстного окна |
| `/reset` | Очистить историю разговора |
| `/help` | Список всех команд |

### Файлы рабочего пространства

Создайте эти файлы в директории `workspace` агента:

| Файл | Назначение |
|------|-----------|
| `CONTEXT.md` | Описание проекта, конвенции кода |
| `IDENTITY.md` | Личность агента, правила поведения |
| `PROFILE.md` | Информация о пользователе |
| `NOTES.md` | Долговременная память агента |
| `notes/YYYY-MM-DD.md` | Ежедневные логи |

### Минимальная сборка (для Raspberry Pi / слабых VPS)

```bash
cargo build --release --no-default-features \
  --features "ollama"
```

Это минимальная рабочая сборка текущей реализации (CLI + Ollama).

### Удалённая оптимизация

Запланированный режим: на слабом устройстве (Pi) использовать мощную машину в сети для оптимизации:

```toml
# На Raspberry Pi
[refiner]
mode = "remote"
url = "http://192.168.1.100:7070"

# На мощной машине
# служба refiner API (пока не реализована)
```

## 1. Видение

Единый бинарник на Rust, который позволяет запускать AI-агентов для кодирования через любую платформу обмена сообщениями, с любым провайдером моделей, на любом оборудовании — от Raspberry Pi до облачного GPU-сервера. Пользователь полностью контролирует своих агентов, модели, память, инструменты и расходы.

### Ключевые преимущества

1. **Ноль зависимостей** — Один скомпилированный бинарник. Никакого runtime, пакетного менеджера или интерпретатора.
2. **Любая модель, любой провайдер** — Claude Code, Anthropic API, OpenAI, HuggingFace, Ollama, vLLM. Переключение прямо в разговоре.
3. **Любое оборудование** — Автоопределение возможностей. 30MB на Pi, 8GB на GPU-сервере.
4. **Экономия токенов** — Опциональный слой оптимизации сокращает расход токенов на 20-70%. Пользователь решает, включать или нет.
5. **Полная прозрачность** — Стоимость токенов, экономия от оптимизации, использование контекста — всё в реальном времени.~
6. **Пользователь владеет всем** — Память, навыки, плагины, конфигурация — обычные файлы на диске под полным контролем.

---

## 2. Основные принципы

1. **Единый бинарник** — Собрать один раз, запускать везде. Без Node.js, Python или npm.
2. **Контроль пользователя** — Ничего не навязывается. Пользователь выбирает модели, точность, оптимизацию, баланс затрат.
3. **Модель-агностичность** — Каждый LLM-бэкенд — полноценный. Без привязки к вендору.
4. **Адаптация к оборудованию** — Грациозная деградация от облачного GPU до Raspberry Pi.
5. **Экономия токенов** — Опционально. Выключено по умолчанию. Пользователь включает, когда хочет экономить.
6. **Прозрачность** — Видимость стоимости и контекста в реальном времени.
7. **Расширяемость** — Пайпы, движки, плагины, навыки — всё подключаемое через трейты и конфигурацию.

## 3. Архитектура

### 3.1 Структура крейтов

```
tengu-cluster/
├── Cargo.toml              # Корень воркспейса + точка входа бинарника
├── src/main.rs             # CLI точка входа
├── crates/
│   ├── tengu-core/         # Общие типы, трейты, конфигурация, маршрутизация
│   ├── tengu-backends/     # Реализации движков (провайдеры моделей)
│   ├── tengu-channels/     # Реализации пайпов (платформы обмена сообщениями)
│   ├── tengu-optimizer/    # Сжатие промптов и оптимизация токенов
│   └── tengu-memory/       # Многоуровневое хранилище знаний и поиск
├── config.example.toml
└── PRD.md
```

### 3.2 Терминология

| Термин Tengu | Что это |
|--------------|---------|
| **Hub** | Центральный сервер — управляет всеми соединениями, маршрутизацией, сессиями |
| **Agent** | Изолированная AI-сущность со своим рабочим пространством, памятью, сессиями и движком |
| **Engine** | AI-бэкенд, питающий агента (Claude Code, Anthropic API, Ollama и др.) |
| **Pipe** | Подключение к платформе обмена сообщениями (Telegram, Discord, CLI, WebChat) |
| **Workspace** | Рабочая директория агента — файлы, документация, контекст проекта |
| **Store** | База знаний агента — индексированные файлы, эмбеддинги, краткие версии |
| **Skill** | Способность, определённая в markdown, которую агент загружает по запросу |
| **Kit** | Набор инструментов агента (файловые операции, shell, веб и др.) |
| **Flow** | Сессия разговора с историей и управлением контекстом |
| **Lens** | Режим точности, управляемый пользователем (eco/standard/precise) |

### 3.3 Поток данных

```
Pipe (Telegram/Discord/CLI/WebChat)
  → Router (привязки агентов, детерминированное сопоставление)
    → Flow Manager (разрешение/создание сессии, загрузка истории)
      → Refiner (опционально: сжатие промпта, удаление шума)
        → Store (опционально: извлечение релевантных знаний)
          → Prompt Assembler (навыки, идентичность, контекст рабочего пространства)
            → Engine (Claude Code / Anthropic / OpenAI / Ollama / HF)
              → Stream Processor (разбиение по лимитам платформы)
                → Pipe (доставка ответа)
```

## 4. Пайпы (Платформы обмена сообщениями)

### 4.1 Трейт Pipe

Каждая платформа реализует трейт `Pipe` с опциональными подтрейтами:

```rust
#[async_trait]
trait Pipe: Send + Sync {
    fn id(&self) -> &str;
    fn display_name(&self) -> &str;

    // Жизненный цикл
    async fn connect(&self, ctx: PipeContext) -> Result<()>;
    async fn disconnect(&self) -> Result<()>;

    // Исходящие
    async fn send_text(&self, target: &Recipient, text: &str, opts: &DeliveryOptions) -> Result<()>;
    async fn send_media(&self, target: &Recipient, media: &MediaPayload) -> Result<()>;

    // Политика
    fn access_policy(&self) -> AccessPolicy;
    fn capabilities(&self) -> PipeCapabilities;

    // Опциональные возможности
    fn streaming(&self) -> Option<&dyn StreamCapable> { None }
    fn threading(&self) -> Option<&dyn ThreadCapable> { None }
    fn approval(&self) -> Option<&dyn ApprovalCapable> { None }
    fn groups(&self) -> Option<&dyn GroupCapable> { None }
}
```

### 4.2 Поддерживаемые пайпы

| Пайп | Статус | Примечание |
|------|--------|------------|
| CLI (stdin/stdout) | Реализовано | `crates/tengu-channels/src/cli/mod.rs` |
| WebChat (HTTP + WS) | Запланировано | Пока только scaffold в конфиге/фичах |
| Telegram | Запланировано | Пока только scaffold в конфиге/фичах |
| Discord | Запланировано | Пока только scaffold в конфиге/фичах |
| Slack | Запланировано | Целевой PRD-объём |
| WhatsApp | Запланировано | Целевой PRD-объём |
| Signal | Запланировано | Целевой PRD-объём |

### 4.3 Политики доступа

| Политика | Поведение |
|----------|-----------|
| `approval` (по умолчанию) | Неизвестные отправители должны быть одобрены. Коды истекают через 1ч. |
| `allowlist` | Только предварительно одобренные отправители |
| `open` | Принимать все входящие сообщения |
| `disabled` | Игнорировать все сообщения |

### 4.4 Маршрутизация сообщений

Детерминированные правила привязки, побеждает наиболее специфичное:

1. Точное совпадение отправителя
2. Совпадение родительского потока
3. Совпадение сервер + роль (Discord guilds)
4. Совпадение сервера
5. Совпадение команды (Slack)
6. Совпадение аккаунта
7. Совпадение на уровне пайпа
8. Откат на агента по умолчанию

Несколько полей совпадения требуют выполнения всех условий (И).

### 4.5 Разбиение ответов

Длинные ответы разбиваются по лимитам платформы:
- Мягкое разбиение с предпочтением параграфов
- Учёт блоков кода (переоткрытие ограждений при разбиении)
- Лимиты текста для каждого пайпа
- Объединение: буферизация мелких частей с таймером ожидания перед отправкой
- Режимы: `off`, `partial` (редактирование на месте для Telegram), `block` (отдельные сообщения)

## 5. Агенты

### 5.1 Изоляция агентов

Каждый агент полностью изолирован:

```rust
struct Agent {
    id: String,
    name: String,
    workspace: PathBuf,          // Рабочая директория

Структура директорий:
```

│       ├── auth/               # Профили аутентификации по провайдерам

│       ├── store/              # Индекс знаний (SQLite)
│       └── workspace/          # Рабочая директория агента
│           ├── CONTEXT.md      # Руководства по проекту
│           ├── IDENTITY.md     # Личность агента

│           ├── NOTES.md        # Постоянная память

### 5.2 Файлы рабочего пространства

| Файл | Назначение | Когда загружается |
|------|-----------|-------------------|
| `CONTEXT.md` | Руководства проекта, конвенции репозитория | Всегда при старте flow |
| `IDENTITY.md` | Личность агента, правила поведения | Первым при старте flow |
| `PROFILE.md` | Информация о пользователе | Вторым при старте flow |
| `NOTES.md` | Долговременная курируемая память | Только прямые сессии |

## 6. Движки (AI-бэкенды)

### 6.1 Трейт Engine

```rust
#[async_trait]
trait Engine: Send + Sync {
    fn id(&self) -> &str;
    fn context_window(&self) -> usize;
    fn supports_tool_use(&self) -> bool;
    fn manages_own_workspace(&self) -> bool;

    async fn run(
        &self,
        messages: &[Message],
        tools: &[ToolDef],
        context: &EngineContext,
    ) -> Result<Pin<Box<dyn Stream<Item = StreamEvent>>>>;
}
```

### 6.2 Поддерживаемые движки

| Движок | Статус | Примечание |
|--------|--------|------------|
| `ollama` | Реализовано | Нестриминговый запрос/ответ через `/api/chat` |
| `anthropic` | Запланировано | Пока scaffold фичи, цель: typed REST |
| `openai` | Запланировано | Пока scaffold фичи, цель: typed REST |
| `google` | Запланировано | Пока scaffold фичи, цель: typed REST |
| `huggingface` | Запланировано | Пока scaffold фичи, цель: `hf-hub` |
| `candle-local` | Запланировано | In-process локальный inference, приоритет CUDA/Metal, CPU fallback |

### 6.3 Переключение движка в процессе чата

Текущее поведение:
- `/engine` показывает текущий движок/модель и размер контекста.
- Переключение через `/engine <name>` пока не реализовано.

Запланировано:
- Переключение движка/модели в середине диалога с безопасной компрессией контекста.

### 6.4 Провайдеры моделей

```rust
#[async_trait]
trait ModelProvider: Send + Sync {
    fn provider_id(&self) -> &str;
    fn list_models(&self) -> Vec<ModelInfo>;

    async fn chat(
        &self,
        model: &str,
        messages: &[Message],
        tools: &[ToolDef],
        auth: &AuthConfig,
    ) -> Result<Pin<Box<dyn Stream<Item = StreamEvent>>>>;
}
```

Формат провайдера: `provider/model` (напр., `anthropic/claude-sonnet-4-5`, `ollama/deepseek-coder-v2`).

Политика зависимостей:
- Предпочитаем официальные SDK провайдера при их наличии и активной поддержке.
- Если официального Rust SDK нет, используем typed direct REST по официальной API-документации.
- Не используем сторонние multi-provider abstraction crates в core runtime.

### 6.5 Профили аутентификации

Для каждого агента, для каждого провайдера:
- Ротация профилей при ошибке
- Отслеживание кулдауна неудачных учётных данных
- Несколько методов аутентификации: API-ключ, OAuth, AWS SDK
- Разрешение переменных окружения

### 6.6 Фейловер

1. Основная модель с первым профилем аутентификации
2. Ротация профилей внутри провайдера
3. Переход к следующей модели в списке
4. Понижение уровня размышлений при переполнении контекста

## 8. Потоки (Сессии)

Текущий статус: состояние потока хранится только в памяти процесса и теряется после перезапуска.

### 8.1 Хранение потоков

Текущий рантайм:
- Только in-memory (персистентности пока нет).

Целевая модель хранения:
- **Индекс потоков (`flows/index.json`)**:
  - отображает `flow_key -> metadata` (`transcript_path`, `updated_at`, `message_count`, `token_estimate`, `last_compacted_at`).
- **Файлы транскриптов (`*.jsonl`)**:
  - append-only журнал событий по каждому потоку (user/assistant/tool/system).
  - удобен для последовательной записи, бэкапов и восстановления после сбоев.

Важно: размер JSONL-файла сам по себе **не** равен токенам, отправляемым в модель.
В промпт всегда загружается только бюджетированное подмножество.

### 8.2 Области видимости потоков

| Область | Паттерн ключа |
|---------|---------------|
| `main` (по умолчанию) | `<agentId>:main` — все ЛС в одном потоке |
| `per-sender` | `<agentId>:dm:<senderId>` |
| `per-pipe-sender` | `<agentId>:<pipe>:dm:<senderId>` |
| `per-group` | `<agentId>:<pipe>:group:<groupId>` |

### 8.3 Сброс потока

| Режим | Поведение |
|-------|-----------|
| `manual` | Только через команду `/reset` |
| `daily` | Автосброс каждые 24ч |
| `idle` | Автосброс после N минут бездействия |

### 8.4 Компактирование

Цель: удерживать prompt в фиксированных границах даже при бесконечном росте истории.

Сборка prompt на каждый ход (цель):
1. Зарезервировать бюджет ответа (output).
2. Разделить входной бюджет на корзины:
   - system/static context
   - окно последних сообщений
   - извлечённые знания
   - summary-блоки после compact
3. Загружать сначала самые новые сообщения до лимита окна.
4. При необходимости подмешивать summary-блоки вместо старых сырых сообщений.
5. Никогда не загружать весь JSONL-транскрипт в prompt.

Стратегия compact (цель):
1. Оставить последние N ходов без изменений.
2. Суммаризировать старые непрерывные диапазоны.
3. В активном окне заменить старые диапазоны ссылками на summary-блоки.
4. Пересчитать `token_estimate` в индексе потока.
5. Сырой транскрипт сохранить на диске для аудита/воспроизведения.

### 8.5 Политика хранения потоков

Целевые правила эксплуатации:
- Ротация больших файлов транскриптов (по размеру), один активный append-файл.
- Малый индекс потоков для O(1)-загрузки на старте.
- Retention/pruning архивов по возрасту и активности.
- Артефакты compact хранить отдельно (не переписывать сырую историю).

### 8.6 Критические разрывы относительно OpenClaw (Storage)

Текущие разрывы реализации, блокирующие production-уровень хранения потоков:
Подробный сравнительный разбор: `STORAGE_RETRIEVAL_GAP_ANALYSIS.md`.

| Разрыв | Почему это важно | Приоритет |
|--------|------------------|-----------|
| Нет персистентного индекса потоков/записи транскриптов | После перезапуска теряется вся история потоков | P0 |
| Нет атомарной записи + дисциплины lock при обновлении индекса | Риск повреждения индекса при конкурентной записи/сбое | P0 |
| Нет валидации/санитизации путей транскриптов | Риск небезопасных путей и проблем восстановления | P0 |
| Нет runtime-сборщика prompt-окна по бюджетным корзинам | Бюджеты токенов описаны в docs, но не enforced в рантайме | P0 |
| Нет исполняемого пути compact (overflow/threshold triggers) | Длинные потоки неизбежно упираются в context window | P0 |
| Нет политики лимита ходов истории по типу потока | Контекст растёт слишком быстро и непредсказуемо | P1 |
| Нет retention/rotation задач для транскриптов | Хранилище растёт без lifecycle-контроля | P1 |
| Нет пути детекта/repair повреждённых транскриптов | Один битый транскрипт ломает непрерывность потока | P1 |

## 9. Store (Система знаний)

Текущий статус: `KnowledgeStore` реализован как in-memory компонент и пока не подключён к основному chat-loop.

### 9.1 Индексация знаний

Текущая реализация:
- In-memory хранение `Vec<KnowledgeEntry>`.
- API для ingest и генерации summary.
- Ранжирование релевантности (path + keyword match).
- Lens-aware выбор представления контента.
- API бюджетированного извлечения (`query_with_budget`).

Запланированная эволюция:
- Персистентный индекс, семантический поиск, авто-реиндексация и более точный ranking.

### 9.2 Двухуровневое извлечение (инновация Tengu)

Каждый проиндексированный файл имеет два представления:

| Уровень | Содержимое | Когда использовать |
|---------|-----------|-------------------|
| **Краткое** | Сжатая версия (10-20% от оригинала) | Быстрое, дешёвое извлечение |
| **Полное** | Оригинальное содержимое | Точное, детальное извлечение |

Контракт извлечения (цель):
- Извлечение обязательно ограничено одновременно `top_k` и `max_tokens`.
- Сначала ранжирование, потом жадная упаковка в бюджет.
- При исчерпании бюджета низкоприоритетные результаты отбрасываются (budget overflow запрещён).

### 9.3 Lens (Режимы точности)

Пользователь управляет используемым уровнем:

| Команда | Режим | Поведение |
|---------|-------|-----------|
| `/eco` | Эко (по умолчанию) | Только краткие версии. Самый дешёвый. |
| `/standard` | Стандартный | Summary-first (сейчас поведение извлечения совпадает с Eco). |
| `/precise` | Точный | Всегда полное содержимое. Максимум токенов. |

Когда refiner выключен (`off`), всё работает как полное содержимое (краткие версии не генерируются).

### 9.4 Провайдеры эмбеддингов

Фазовый план извлечения:

| Фаза | Режим извлечения | Профиль стоимости | Примечание |
|------|------------------|-------------------|------------|
| Текущая | Keyword/path scoring | Минимальный | Ноль внешних зависимостей, быстро для малого/среднего workspace |
| Следующая | TF-IDF / lexical ranking | Низкий | Лучшая релевантность без ML-зависимостей |
| Опциональная | Embeddings (local/API) | Выше | Только при необходимости по масштабу/качеству |

Провайдеры embeddings (опциональная фаза):
- OpenAI/Gemini API, локальный Candle, либо pure-Rust fallback стратегии.

### 9.5 Жёсткие токенные ограничения

Неприменимые к компромиссам правила контроля стоимости:
- Бюджет извлечения независим от бюджета истории потока.
- `Lens::Eco` по умолчанию использует только summary-извлечение.
- Полный контент (`Lens::Precise`) — только явно и всё равно под budget cap.
- Сборка prompt работает в режиме fail-closed: при риске переполнения отбрасывается низкоприоритетный контекст.

### 9.6 Критические разрывы относительно OpenClaw (Retrieval)

Текущие разрывы реализации, блокирующие надёжное извлечение:
Подробный сравнительный разбор: `STORAGE_RETRIEVAL_GAP_ANALYSIS.md`.

| Разрыв | Почему это важно | Приоритет |
|--------|------------------|-----------|
| `KnowledgeStore` не подключён к chat-loop | Контроль качества/стоимости retrieval не работает в рантайме | P0 |
| Нет персистентного retrieval-индекса | Переиндексация на каждом старте увеличивает cold-start latency | P1 |
| Нет chunking для больших файлов | Один большой документ может «съесть» весь retrieval-бюджет | P1 |
| Нет citation-метаданных (line/offset refs) | Слабая проверяемость и объяснимость ответов | P1 |
| Нет telemetry качества retrieval (hit rate, dropped-by-budget) | Нечем точно тюнить токены/стоимость на данных | P1 |

## 11. Refiner (Слой оптимизации)

### 11.1 Режимы Refiner

| Режим | Описание | Расход ресурсов |
|-------|----------|-----------------|
| `off` | Без обработки. Прямая передача. | 0 |
| `rules` | Регулярные выражения + эвристическое сжатие. Без ML. | ~0 |
| `local` | Candle — ML-модели в процессе. | 300MB-8GB |
| `remote` | Делегирование на другой экземпляр Tengu в сети. | ~0 (клиент) |

### 11.2 Трейт Refiner

```rust
#[async_trait]
trait Refiner: Send + Sync {
    async fn compress(&self, input: &str) -> Result<String>;
    async fn embed(&self, text: &str) -> Result<Vec<f32>>;
    async fn summarize(&self, content: &str, max_tokens: u32) -> Result<String>;
    fn memory_footprint(&self) -> usize;
}
```

Реализации: `NoopRefiner`, `RuleRefiner`, `CandleRefiner`, `RemoteRefiner`.

### 11.3 Сжатие на основе правил (нулевая стоимость)

- Удаление слов-паразитов ("basically", "just", "maybe", "perhaps")
- Удаление хеджирования ("I think", "could you maybe")
- Сжатие пробелов, дедупликация фраз
- Скомпилированные regex-паттерны — задержка микросекунды
- Экономия 20-40% токенов

### 11.4 ML-сжатие (Candle)

- Маленькая квантованная модель в процессе (Phi-3-mini, SmolLM2, Qwen2.5-1.5B)
- Семантическое сжатие с сохранением намерения
- Путь ускорения: при наличии использовать CUDA/Metal, иначе CPU fallback
- Явная цель: максимально использовать локальные ресурсы для ускорения/удешевления оптимизации
- ~5-50мс на сообщение
- Экономия 60-70% токенов
