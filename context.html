Context · what the LLM actually sees, layer by layer

Seven shaping layers + one observability layer. ~27 distinct mechanisms. Zero LLM-summarisation passes — everything is mechanical.

A user message hits Layers 1 → 2 → 3 (potentially → 4) on the planner-side turn, then Layers 5 → 3 (→ 4) on each subagent step. Layers 0, 6, 7 are infrastructure consumed by the others. Layer 8 is observability — it watches the bytes without changing them.

What the planner sees vs what the subagent sees

Two different prompts, two different scopes. The planner sees a ranked roster of agents+skills+tools (descriptions only). The subagent it dispatches sees its own declared skills (full bodies) and its own tool allow-list — no roster.

Tools stripped (tools=[]), memory injection off, grounding nudge suppressed. The planner has exactly one job: emit plan JSON whose agent field matches one of the agent names above.

Subagent promptmain.rs::run_agent_subprocess · fresh context
// system message — assembled at subprocess start
<base agent template>
<agent identity.instructions from agents/<name>.toml>

<skill #1 body — full SKILL.md, frontmatter stripped>
<skill #2 body>
...                                          // every skill in spec.skills array

<mandatory suffix — compress_and_store reminder>

// tools available this turn (NOT in prompt — registered at engine layer)
// (spec.tools ∩ ipc.tools) ∪ {compress_and_store}

// messages — STARTS EMPTY. No parent history.
User: <step.goal — one-sentence instruction from the planner>

No roster. The subagent doesn't know other agents exist — it only sees its declared skills (full bodies) and its tool allow-list. Step output is committed when the model calls compress_and_store → written to tengu_outputs, child exits.

Source: planner.rs::format_roster for the roster shape, main.rs::run_agent_subprocess for the subagent prompt, skills/orchestrator/SKILL.md for the rules the planner LLM follows when reading the roster.
