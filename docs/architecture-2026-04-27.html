Three Qdrant collections — what's in each, who writes, who reads

Collection Holds Written by Read by TTL
tengu_registry Agent specs, skills, tool defs (built-in + MCP) indexer::reindex_all_workspace (CLI + auto on first chat turn) RagPlanner::plan/replan via search_registry NO — deterministic
tengu_messages User messages keyed by session_id RagPlanner::persist_user_message on every plan() RagPlanner::cross_session_recall_block (opt-in via memory.cross_session_msg_top_k) YES — cleanup::ttl_cleanup
tengu_outputs Compressed step output summaries compress_and_store tool (implicit on every subagent) RagPlanner::replan for cross-plan recall YES — cleanup::ttl_cleanup

All three live in Qdrant (gRPC). Embedding model: text-embedding-3-small (1536d). When the qdrant cargo feature is off, this entire layer is unavailable and the orchestrator cannot run — channels fall back to direct default-agent dispatch.

Six things that surprised me reading this code

The doctrine is real and the boundaries are enforced. These are the load-bearing details that don't show up in any single function.

Doctrine

A. LLM = heart, RAG = brain, tools = hands

RagPlanner does ONE thing — pick the right agent. Its LLM call strips tools, tool_executor, memory_manager, and grounding so the planner has only one job: emit plan JSON. Subagents do the actual work in their own subprocess.

channel_runtime::run_turn_with_system
Open question

B. Two senses of "session_id"

RagPlanner mints one (TENGU_SESSION_ID env override or fresh UUID). SubprocessRunner mints its own. They don't share — open question in the handoff. Parent's id stamps user messages in tengu_messages; child's id stamps step outputs in tengu_outputs.

orchestrator/planner.rs:RagPlanner.session_id · runner.rs:session_id
Phase 7.2 fix

C. Sandbox config crosses the IPC boundary

Without this, the child loaded ~/.tengu/config.toml not the parent's sandbox config. Symptom: http_request scope-denies in researcher even when the parent's sandbox allowed "*". Fix: AgentIpcInput.sandbox_config field, threaded from Config.sandbox_name → SubprocessRunner → IPC.

Config.sandbox_name (#[serde(skip)]) · load_sandbox_or sets it
Implicit contract

D. compress_and_store is implicit, not declared

Never list compress_and_store in agents/*.toml::tools — the runner appends it to every subagent automatically. Used to mark "I'm done." Middle-ground protocol: only Failed when no text emitted AND no compress_and_store called. Otherwise OK with a tracing warn.

main.rs::run_agent_subprocess (Phase 5c)
Two layers

E. Two layers of recall in the planner prompt

In-memory ring buffer (Phase 6.4 lite) — recent user msgs THIS process, lost on restart. Cross-session block (Phase 6.4 full) — semantic search over tengu_messages, opt-in via memory.cross_session_msg_top_k. Both inject before the current turn.

RagPlanner::update_and_format_history + cross_session_recall_block
Multi-turn UX

F. C → B fallback — composed agents, two turns

Turn 1 (C): planner emits Direct asking the user to confirm closest match. Turn 2 (B): on confirmation, planner emits Plan with Step.compose set. Runner loads the base agent, OVERRIDES skills+tools for this run only. No persistence — file on disk unchanged.

orchestrator/plan.rs::AgentCompose (Phase 6.7)
Phase 7.3

G. AgentSpec.engine — subagents pick their backend

Each agent's TOML can declare engine = "openrouter" (default) or engine = "claude_code". Subprocess honours it via build_engine. Model slug format depends on engine: OpenRouter wants anthropic/claude-sonnet-4-6; Claude Code wants bare claude-sonnet-4-6. Mixed-mode (planner = OpenRouter, subagents = Claude Code) is the verified pattern — Claude Code as planner bypasses orchestration because its MCP tool access is set at engine-construction time.

agents/<name>.toml::engine — agent_config_from_spec — build_engine
Phase 7.4

H. Claude Code subagents see tengu's tools via MCP

SubprocessRunner sets EngineContext.bridge_tools = Some(tools) when spec.engine == "claude_code". Claude Code spawns tengu mcp-bridge as an MCP server, which advertises tengu's tools as mcp__tengu-tools__<name>. Claude Code calls those, the bridge dispatches to its own ToolRegistry, response flows back. Two key env vars forwarded to the bridge: TENGU_SESSION_ID and OPENROUTER_API_KEY (without them the bridge silently fails to register memory tools).

EngineContext.bridge_tools — claude_code_engine.rs::build_mcp_config_json — mcp_bridge.rs::build_bridge_executor
Phase 7.4

I. parse_verdict prose-fallback

Claude Code is conversational by default; even with the SKILL.md instructing JSON-only, the planner LLM sometimes emits prose. Pre-7.4 this produced System error: orchestrator initial call failed. Now parse_verdict wraps any unparseable text as Direct { response } with a warn log. User sees the model's reply; logs show when it's firing so you can tune.

orchestrator/planner.rs::parse_verdict — Path 4 fallback
Phase 7.7

J. Adding a tool is a one-place edit

Pre-7.7 tool registration was duplicated in channel_runtime::build_tool_executor AND mcp_bridge::build_bridge_executor; fixing one and forgetting the other was the root cause of the Bug B/Bug C debacle. Now register_core_plugins is the single registration site for the seven shared plugins (workspace, memory, cache, skill-lifecycle, compress_and_store, http, crypto). The bridge calls it; the in-process executor calls it. SkillPlugin + McpPlugin stay outside (they need inputs the bridge can't sensibly provide).

channel_runtime::register_core_plugins — CoreRegistrationOpts
Phase 7.7

K. WORKSPACE_TOOLS_ALLOWLIST — single constant

The three opt-in workspace tools (shared_cache, persistent_store, skill_distill) used to live in two constants in two files. Now there's one pub(crate) const WORKSPACE_TOOLS_ALLOWLIST in channel_runtime.rs. Adding a fourth opt-in is a one-line edit. agent_config_from_spec filters spec.tools against it; the bridge filters allowed_names against it.
