Tengu session memory — recall failure debug map

2026-05-11 · investigates "why can't the planner remember what I just said?" · interactive — toggle knobs to simulate alternative configs

Verdict: the data isn't broken — by default, almost nothing is asked for, and what is asked for is asked for the wrong way.

Three orthogonal failures stack:

  1. Defaults are OFF. memory.enabled=false, within_session_output_top_k=0, cross_session_msg_top_k=0. Out of the box the planner gets only the in-process user-message ring buffer (10 msgs, user side only, lost on restart).
  2. The planner is amnesic about its own replies. When the verdict is Direct (no subagent dispatched), the response is never written to agentic_memory step outputs on the TUI/chat path — only the webhook path persists Direct verdicts (Fix H). Ring buffer pushes user messages only. So turn N+1 sees [M1, M2] but never sees R1.
  3. Open Brain / Karpathy LLM Wiki is the wrong primitive for dialog continuity. Cosine similarity ≠ recency; short utterances ("yes", "do it") embed near-randomly; "the molecule project" is coreference, not similarity; current message self-matches its own paraphrase from 3 turns ago. Vector recall is fine for cross-session search-my-history; it is a poor substitute for a verbatim last-N window.

Five-line repro of the bug: enable nothing, type "remember pi is 3.14", on the next turn type "what's pi?" — the planner has no record of the first turn (no subagent, no compress_and_store, no Fix C backstop, no Fix H), no within-session output knob to read it back, and ring-buffer history shows only your user messages. tengu memory inspect --session $TENGU_SESSION_ID confirms zero rows.

3 · Two-turn lifecycle — where dialog drops on the floor

Scenario: user types M1 on turn N; planner emits Direct{response:R1}; user types M2 on turn N+1 referring to R1. Trace shows what's persisted, read, and dropped at each step.

Turn N · write User msg M1 → RagPlanner.session_history.push(M1) (in-RAM ring buffer, USER side only) planner.rs:377
Turn N · write persist_user_message(M1) → agentic_memory user events row, session_id=$sid, step_id=None planner.rs:553
Turn N · read search_registry_with_vec on TENGU_PLANNER_REGISTRY.md for roster; top 20 agents/skills/tools (score floor ~0.15, no threshold filter)
Turn N · build Planner combines: system + roster + cross_session_block (empty, OFF) + history_block (just M1) + session_recall (empty, OFF) + user_message
Turn N · build run_turn_with_system nils memory_manager for this call — chat-side recall NEVER fires channel_runtime.rs ≈ 1140–1143
Turn N · LLM Planner emits {"kind":"direct","response":"R1"}
Turn N · drop AMNESIA #1 R1 is NEVER pushed into session_history (ring buffer ignores assistant side) planner.rs:378–389
Turn N · drop AMNESIA #2 R1 is NEVER persisted to agentic_memory step outputs on TUI path — Fix H persists Direct only on webhook path webhook_builder.rs::run_one_shot
Turn N · drop AMNESIA #3 R1 is NEVER persisted to agentic_memory user events either (that's user-msgs-only)
Turn N · UI R1 lands in chat state.messages as Assistant. Useful only on the chat-engine path — bypassed when planner is entry point.
Turn N+1 · write User msg M2 → ring buffer push, agentic_memory user events write (same as before)
Turn N+1 · read cross_session_recall_block: empty (knob=0)
Turn N+1 · read session_output_recall_block (Fix A): empty (knob=0; also nothing written in turn N)
Turn N+1 · read history_block = "1. M1" (NO R1, NO M2 — M2 is shown separately as current turn)
Turn N+1 · build AMNESIA #4 Planner sees only its own roster + your previous user message. It cannot see its own R1. If M2 = "what did you just tell me?" the planner has to guess.
Turn N+1 · LLM If planner dispatches a subagent, see next…
Subagent · IPC AMNESIA #5 Child receives only goal + ids in AgentIpcInput. No messages, no prior turns, no R1, no M1. runner.rs:24–69
Subagent · IPC AMNESIA #6 Subagent's own working context: empty messages array. Its only handle on dialog is the one-sentence goal the planner wrote. main.rs::run_agent_subprocess ≈ 845
Subagent · end AMNESIA #7 If subagent doesn't call compress_and_store, Phase 5c + Fix C save the final text — but only for subagent-dispatched turns. Direct verdicts don't reach this code path.

4 · Open Brain / Karpathy LLM Wiki mechanics — why retrieval is mediocre even when enabled

MechanismBehaviourConsequence for dialog recallCite
Embedder = text-embedding-3-small Cosine, 1536-dim. CLAUDE.md acknowledges score floor ~0.15. Registry-tier scores cap at 0.30–0.40 for clearly-relevant matches. Score is a noise floor, not a real threshold. Marginal hits (0.18) are returned. CLAUDE.md "Registry score floor"; config.rs:789
No score-threshold filter in search code search_outputs_for_session_with_vec applies session filter, but never score >= X. Top-K is taken regardless. Irrelevant rows in the recall block. Worse: planner LLM may trust them and answer wrong. rag/query.rs
2× over-fetch post-Fix-F Fix F pushed session filter to legacy vector DB; over-fetch dropped from 5× to 2×. Thin margin: if session-filtered subset is sparse, you get <K rows. No re-fetch loop. CLAUDE.md "Fix F"; rag/query.rs
compress_and_store writes ONE row per summary No chunking. Fix D char-caps at 24 000 chars; everything past is discarded with a marker. Tail content past 24K is permanently invisible to retrieval. Long pipeline summaries are lossy on the back end. compress_and_store.rs:54–82
Self-similarity of current message The current user message is embedded; recall returns past user messages similar to it. Often the most similar match is the user's own prior phrasing. Recall surfaces the user's own words back at the planner. Adds noise, not signal. planner.rs:451–459 (exact-match filter — only catches literal duplicates, not paraphrases)
Short-utterance embeddings "yes", "do it", "no, the second one" → low-magnitude embedding vectors with high noise. On confirmation turns the recall block returns essentially random hits. Inherent to embedding models, not tengu-specific
Coreference "the molecule project" has no shared tokens with the prior step's actual content. Vector search misses pronoun/alias-style references entirely. This is the most common dialog-continuity failure mode. —
No vector_size validation Config vector_size is used verbatim at collection creation. Mismatch with embedder dim ⇒ silent write failure on upsert. Misconfig disappears data with no runtime error. rag/vector/qdrant.rs:66
Embed-call fail-soft Fix E caches the user-message embedding once per turn. If that one call fails, every downstream lane gets None and degrades. Logged at warn. One blip in OpenRouter embed quota ⇒ silent recall miss for that turn. planner.rs:701–714
Write durability UpsertPointsBuilder.wait(true) ⇒ legacy vector DB returns when point is indexed. Immediate next-turn read sees the write. OK. No async-gap. (This is one of the few things not broken.) rag/vector/qdrant.rs:194

5 · Is Open Brain / Karpathy LLM Wiki even the right primitive for session memory?

Failure modes — Open Brain / Karpathy LLM Wiki for dialog

ModeWhy it breaks
Recency ≠ similaritycosine has no time axis; top-K can return a turn from 30 min ago over the last turn
Window-not-snippetcontinuity needs the whole last N pairs verbatim; top-K gives 1–2 chunks and loses the thread
Short-utterance noise"yes" / "do it" embed near-random
Self-similaritycurrent message ≈ paraphrase of recent ones; model gets its own words echoed back as "context"
Coreference miss"the molecule project" can't be resolved by token overlap

Recommended doctrine update

Today: "LLM = heart, Open Brain / Karpathy LLM Wiki = brain, tools = hands." Single memory primitive carries cross-session search and dialog continuity.

Proposed: "LLM = heart, working memory = scratchpad, Open Brain / Karpathy LLM Wiki = long-term brain, tools = hands."

Same composition principle the rest of the harness already uses for agents/skills/tools. Open Brain / Karpathy LLM Wiki keeps the cross-session "search my history" job; a deterministic last-N window + a per-session working-memory record handles continuity. This matches MemGPT's paging metaphor, OpenSearch's working/long-term split, and the A-MEM episodic/semantic distinction.

You do not need to migrate to OpenSearch. legacy vector DB + a flat per-session JSON (under .tengu/sessions/<id>.json) + a verbatim ring buffer get the same shape with less infra churn. Revisit only if hybrid keyword+vector or built-in fact-extraction become real needs.

7 · Diagnose your current session — exact commands

Before changing code, prove which surface is empty. The CLAUDE.md mentions tengu memory inspect as the canonical diagnostic.

# 1) Pin a session_id so you can recall later
export TENGU_SESSION_ID=$(uuidgen)
echo "session: $TENGU_SESSION_ID"

# 2) Start a chat with verbose logging
RUST_LOG=tengu=info cargo run --release --features qdrant -- chat --sandbox <name>
# Type one message — say something memorable — then exit.

# 3) Inspect what was written
cargo run --release --features qdrant -- memory inspect --session $TENGU_SESSION_ID
# Expect: user message row in agentic_memory user events. If a Direct verdict was issued
# and no subagent ran, there should be ZERO rows in agentic_memory step outputs. This is
# the bug. If a subagent ran, expect ONE row per compress_and_store call.

# 4) Inspect by collection
cargo run --release --features qdrant -- memory inspect --session $TENGU_SESSION_ID --collection outputs
cargo run --release --features qdrant -- memory inspect --session $TENGU_SESSION_ID --collection messages

# 5) Verify the unified session_id (Fix B) is intact across IPC
grep "session_id=$TENGU_SESSION_ID" <your-log-file> | head -20

If memory inspect returns zero rows for outputs, check this checklist in order:

  1. memory.enabled = true in sandboxes/<name>/config.toml?
  2. Built with --features qdrant?
  3. Did the turn actually dispatch a subagent, or did the planner emit Direct? (Direct verdicts on TUI path write nothing.)
  4. If a subagent ran: did compress_and_store fire? Look for the Fix C backstop log line compress_and_store: backstop wrote final_text summary to agentic_memory step outputs.
  5. Was the summary > 24K chars? Look for the Fix D log compress_and_store: summary truncated to fit embedder input cap.
  6. Did the embedder succeed? RUST_LOG=tengu=debug for embedder errors.
