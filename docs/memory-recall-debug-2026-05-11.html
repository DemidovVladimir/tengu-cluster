Tengu session memory — recall failure debug map

2026-05-11 · investigates "why can't the planner remember what I just said?" · interactive — toggle knobs to simulate alternative configs

Verdict: the data isn't broken — by default, almost nothing is asked for, and what is asked for is asked for the wrong way.

Three orthogonal failures stack:

  1. Defaults are OFF. memory.enabled=false, within_session_output_top_k=0, cross_session_msg_top_k=0. Out of the box the planner gets only the in-process user-message ring buffer (10 msgs, user side only, lost on restart).
  2. The planner is amnesic about its own replies. When the verdict is Direct (no subagent dispatched), the response is never written to agentic_memory step outputs on the TUI/chat path — only the webhook path persists Direct verdicts (Fix H). Ring buffer pushes user messages only. So turn N+1 sees [M1, M2] but never sees R1.
  3. Open Brain / Karpathy LLM Wiki is the wrong primitive for dialog continuity. Cosine similarity ≠ recency; short utterances ("yes", "do it") embed near-randomly; "the molecule project" is coreference, not similarity; current message self-matches its own paraphrase from 3 turns ago. Vector recall is fine for cross-session search-my-history; it is a poor substitute for a verbatim last-N window.

Five-line repro of the bug: enable nothing, type "remember pi is 3.14", on the next turn type "what's pi?" — the planner has no record of the first turn (no subagent, no compress_and_store, no Fix C backstop, no Fix H), no within-session output knob to read it back, and ring-buffer history shows only your user messages. SELECT count(*) FROM memory_events WHERE session_id = '$TENGU_SESSION_ID' against TENGU_MEMORY_DATABASE_URL confirms zero rows (the tengu memory inspect CLI was removed with the Qdrant path, 2026-05-14).

3 · Two-turn lifecycle — where dialog drops on the floor

Scenario: user types M1 on turn N; planner emits Direct{response:R1}; user types M2 on turn N+1 referring to R1. Trace shows what's persisted, read, and dropped at each step.

Turn N · write User msg M1 → RagPlanner.session_history.push(M1) (in-RAM ring buffer, USER side only) planner.rs:382
Turn N · write persist_user_message(M1) → agentic_memory user events row, session_id=$sid, step_id=None planner.rs:557
Turn N · read load_registry_block reads the file-backed TENGU_PLANNER_REGISTRY.md (regenerated from the [agents.*] blocks that carry a description, plus skills, core tools, MCP tools) (no embedding, no similarity score — the planner LLM reads every entry) planner.rs:336 · shared_files.rs::render_registry
Turn N · build Planner combines: system + roster + cross_session_block (empty, OFF) + history_block (just M1) + session_recall (empty, OFF) + user_message
Turn N · build run_turn_with_system nils memory_manager for this call — chat-side recall NEVER fires bootstrap/:1150
Turn N · LLM Planner emits {"kind":"direct","response":"R1"}
Turn N · drop AMNESIA #1 R1 is NEVER pushed into session_history (ring buffer ignores assistant side) planner.rs:382–394
Turn N · drop AMNESIA #2 R1 is NEVER persisted to agentic_memory step outputs on TUI path — Fix H persists Direct only on webhook path (step_id webhook-handler) adapters/inbound/webhooks.rs::run_one_shot → persist_webhook_output
Turn N · drop AMNESIA #3 R1 is NEVER persisted to agentic_memory user events either (that's user-msgs-only)
Turn N · UI R1 lands in chat state.messages as Assistant. Useful only on the chat-engine path — bypassed when planner is entry point.
Turn N+1 · write User msg M2 → ring buffer push, agentic_memory user events write (same as before)
Turn N+1 · read cross_session_recall_block: empty (knob=0)
Turn N+1 · read session_output_recall_block (Fix A): empty (knob=0; also nothing written in turn N)
Turn N+1 · read history_block = "1. M1" (NO R1, NO M2 — M2 is shown separately as current turn)
Turn N+1 · build AMNESIA #4 Planner sees only its own roster + your previous user message. It cannot see its own R1. If M2 = "what did you just tell me?" the planner has to guess.
Turn N+1 · LLM If planner dispatches a subagent, see next…
Subagent · IPC AMNESIA #5 Child receives only goal + ids in AgentIpcInput. No messages, no prior turns, no R1, no M1 (plan_state carries the accepted plan, not dialog). runner.rs:26–79
Subagent · IPC AMNESIA #6 Subagent's own working context: empty messages array. Its only handle on dialog is the one-sentence goal the planner wrote. adapters/inbound/cli/run_agent.rs::run_agent_subprocess ≈ 858
Subagent · end AMNESIA #7 If subagent doesn't call compress_and_store, Phase 5c + Fix C save the final text — but only for subagent-dispatched turns. Direct verdicts don't reach this code path.

4 · Open Brain / Karpathy LLM Wiki mechanics — why retrieval is mediocre even when enabled

MechanismBehaviourConsequence for dialog recallCite
Embedder = text-embedding-3-small Cosine, 1536-dim, pinned (Postgres schema hardcodes vector(1536)). Used only for the Postgres memory lanes — planner registry routing is file-backed and never embeds. Embed calls go through egress::policy().llm_api_client (Tor by default, [egress] network = "tor"). Score is raw cosine similarity with no floor. Marginal hits (0.18) are returned. config.rs:788; memory/vector/embedder.rs::DEFAULT_EMBEDDING_MODEL; agentic_memory/mod.rs:1029
No score-threshold filter in search code recall_step_outputs_for_session_with_vec filters by session_id / kind in SQL, but never score >= X. Top-K is taken regardless. Irrelevant rows in the recall block. Worse: planner LLM may trust them and answer wrong. outbound/tools/agentic_memory/mod.rs:114, 834
Over-fetch = top_k + 2 Session / kind filters run inside the SQL WHERE; recall_user_messages_with_vec fetches top_k + 2 then drops exact matches of the current message. Thin margin: if the filtered subset is sparse, you get <K rows. No re-fetch loop. outbound/tools/agentic_memory/mod.rs:96–130
Step summary = ONE memory_events row No chunking and no char cap (the Qdrant-era Fix D 24K cap went with Phase 6). An oversize summary fails the embed call and lands text-only (FTS-only recall). Long pipeline summaries lose the vector lane entirely; chunked multi-row writes are still an open item. adapters/inbound/cli/run_agent.rs::try_persist_agentic_step_summary:584; agentic_memory/mod.rs::write_step_summary_with_embedding:41
Self-similarity of current message The current user message is embedded; recall returns past user messages similar to it. Often the most similar match is the user's own prior phrasing. Recall surfaces the user's own words back at the planner. Adds noise, not signal. agentic_memory/mod.rs:107 (exact-match filter — only catches literal duplicates, not paraphrases); recall runs BEFORE persist (planner.rs:661–668)
Short-utterance embeddings "yes", "do it", "no, the second one" → low-magnitude embedding vectors with high noise. On confirmation turns the recall block returns essentially random hits. Inherent to embedding models, not tengu-specific
Coreference "the molecule project" has no shared tokens with the prior step's actual content. Vector search misses pronoun/alias-style references entirely. This is the most common dialog-continuity failure mode. —
Embedding dim validated (1536) pgvector_literal rejects any non-1536 / non-finite vector; the write degrades to a text-only row and recall to FTS-only, at warn. Fixed in Phase 6 — a wrong-dim embedder no longer disappears data, but the vector lane silently drops out (watch the warn line). agentic_memory/mod.rs:585–605, 842–851, 1029
Embed-call fail-soft Fix E caches the user-message embedding once per turn. If that one call fails, every downstream lane gets None and degrades. Logged at warn. One blip in OpenRouter embed quota — or the Tor proxy being down (egress is fail-closed) — ⇒ silent recall miss for that turn. planner.rs:320–334
Write durability Plain INSERT INTO memory_events, committed before the call returns. Immediate next-turn read sees the write. OK. No async-gap. (This is one of the few things not broken.) agentic_memory/mod.rs:585

5 · Is Open Brain / Karpathy LLM Wiki even the right primitive for session memory?

Failure modes — Open Brain / Karpathy LLM Wiki for dialog

ModeWhy it breaks
Recency ≠ similaritycosine has no time axis; top-K can return a turn from 30 min ago over the last turn
Window-not-snippetcontinuity needs the whole last N pairs verbatim; top-K gives 1–2 chunks and loses the thread
Short-utterance noise"yes" / "do it" embed near-random
Self-similaritycurrent message ≈ paraphrase of recent ones; model gets its own words echoed back as "context"
Coreference miss"the molecule project" can't be resolved by token overlap
Threshold theater0.15 floor is "not random," not "relevant"
Embedding cost / quotaevery turn re-embeds; one blip kills recall

Recommended doctrine update

Today: "LLM = heart, Open Brain / Karpathy LLM Wiki = brain, tools = hands." Single memory primitive carries cross-session search and dialog continuity.

Proposed: "LLM = heart, working memory = scratchpad, Open Brain / Karpathy LLM Wiki = long-term brain, tools = hands."

Same composition principle the rest of the harness already uses for agents/skills/tools. Open Brain / Karpathy LLM Wiki keeps the cross-session "search my history" job; a deterministic last-N window + a per-session working-memory record handles continuity. This matches MemGPT's paging metaphor, OpenSearch's working/long-term split, and the A-MEM episodic/semantic distinction.

You do not need to migrate to OpenSearch. Postgres agentic_memory + a flat per-session JSON (under .tengu/sessions/<id>.json) + a verbatim ring buffer get the same shape with less infra churn. Revisit only if hybrid keyword+vector or built-in fact-extraction become real needs.

7 · Diagnose your current session — exact commands

Before changing code, prove which surface is empty. tengu memory inspect was removed with the Qdrant path (2026-05-14) — query Postgres directly via TENGU_MEMORY_DATABASE_URL, or run the ignored postgres_*_smoke tests.

# 0) Postgres + pgvector — loopback / compose-internal, never routed through Tor
docker compose --profile postgres-memory up -d postgres-memory
export TENGU_MEMORY_DATABASE_URL=postgres://tengu:tengu@localhost:5432/tengu_memory

# 1) Pin a session_id so you can recall later
export TENGU_SESSION_ID=$(uuidgen)
echo "session: $TENGU_SESSION_ID"

# 2) Start a chat with verbose logging. Embeddings go through [egress] — Tor by default
#    (`make tor` first, or `[egress] network = "open"` in the sandbox).
RUST_LOG=tengu=info cargo run --release --features postgres_memory -- chat --sandbox <name>
# Type one message — say something memorable — then exit.

# 3) Inspect what was written
psql "$TENGU_MEMORY_DATABASE_URL" -c "SELECT kind, agent, metadata->>'step_id' AS step_id, left(content, 80) AS content FROM memory_events WHERE session_id = '$TENGU_SESSION_ID' ORDER BY created_at"
# Expect: one kind=message row (agent=planner). If a Direct verdict was issued
# and no subagent ran, there should be ZERO kind=step_output rows. This is
# the bug. If a subagent ran, expect ONE step_output row per step (compress_and_store intercept or backstop).

# 4) Count by kind
psql "$TENGU_MEMORY_DATABASE_URL" -c "SELECT kind, count(*) FROM memory_events WHERE session_id = '$TENGU_SESSION_ID' GROUP BY kind"

# 5) Verify the unified session_id (Fix B) is intact across IPC
grep "session_id=$TENGU_SESSION_ID" <your-log-file> | head -20

If the query returns zero step_output rows, check this checklist in order:

  1. memory.enabled = true in sandboxes/<name>/config.toml?
  2. Built with --features postgres_memory, and TENGU_MEMORY_DATABASE_URL set?
  3. Did the turn actually dispatch a subagent, or did the planner emit Direct? (Direct verdicts on TUI path write nothing.)
  4. If a subagent ran: did compress_and_store fire? Look for the Fix C backstop log line agentic_memory: backstop wrote final_text summary to Postgres (or agentic_memory: backstop write FAILED).
  5. Did the summary embed? A text-only row is FTS-only — look for agentic_memory: step summary embedding failed; writing text-only memory.
  6. Did the embedder succeed? RUST_LOG=tengu=debug for embedder errors. Under the default [egress] network = "tor" a down proxy fails the embed call closed — tengu doctor --sandbox <name> --tor.
