Tengu Orchestrator — Pipeline

Harness-owned orchestration, parallel + sequential execution, retention. Every diagram references exact file:line locations in the source tree. Current shape: planner = RagPlanner (file-backed TENGU_PLANNER_REGISTRY.md), worker = SubprocessRunner (one tengu run-agent child per step), step memory = Postgres agentic_memory. Line numbers as of 2026-09-18.

1 · Overview

A user message arrives on a channel (Telegram / TUI / Webhooks / Eval runner). The channel calls Orchestrator::handle(prompt). The planner LLM (tools stripped) emits a JSON plan; a Rust DAG executor dispatches each step as a tengu run-agent subprocess (SubprocessRunner) that runs its own LLM + tools loop; step summaries flow back over IPC as a single final response. No LLM ever sees the orchestration machinery directly.

The three execution patterns on this page:

PatternDAG shapeTested by
Sequentials1 → s2eval row two_step_sequential
Parallel + synthesize(s1, s2, ..., sN) → sMeval row parallel_fan_out
Diamond / mixeds1 → (s2, s3) → s4eval row diamond_dag

T+0.0s orchestrator:plan_created steps=[s1:researcher(deps=[]), s2:writer(deps=[s1])] T+0.1s orchestrator:step_started s1:researcher T+0.1s http_request GET .../Status/200 T+1.4s http_request GET .../Status/404 T+14.2s orchestrator:step_succeeded s1 ← executor enqueues s2 only now T+14.3s orchestrator:step_started s2:writer T+22.8s orchestrator:step_succeeded s2 T+22.9s orchestrator:plan_completed cancelled=false
Invariant: s2.depends_on = [s1], so ready_steps at plan.rs:91 returns [s1] first, then [s2] only after s1 is in completed. The 0.1s gap between s1 succeeded and s2 started is the guarantee.

Core logic

// orchestrator/plan.rs:91
pub fn ready_steps(&self, completed: &HashSet<StepId>) -> Vec<&Step> {
    self.steps
        .iter()
        .filter(|s| {
            !completed.contains(&s.id) && s.depends_on.iter().all(|d| completed.contains(d))
        })
        .collect()
}

depends_on.iter().all(|d| completed.contains(d)) is the ONLY code that decides sequential vs parallel. Everything else falls out from it.

Observed timeline — interleaving as proof of concurrency

T+0.0s orchestrator:plan_created (5 steps) T+0.1s orchestrator:step_started s1 ┐ T+0.1s orchestrator:step_started s2 │ all four start T+0.1s orchestrator:step_started s3 │ within ~100ms T+0.1s orchestrator:step_started s4 ┘ T+0.2s http_request (s3) ← interleaved, proof of tokio::spawn T+0.3s http_request (s1) T+0.3s http_request (s4) T+0.4s http_request (s2) ... Invariant: interleaved tool calls prove concurrent execution. If one researcher were doing all four sequentially, tool calls would be grouped by step (all of s1's, then all of s2's). The interleaving is only possible because tokio::spawn ran the four researchers on independent tasks — each step is its own tengu run-agent child process.

Core logic

// orchestrator/executor.rs:62 — inside the main loop (spawn at :74)
for step in plan.ready_steps(&completed) {
    if in_flight.contains(&step.id) {
        continue;
    }
    let step_inputs = render_step_inputs(step, &completed_outputs);
    // ... clone worker / policy / events / step ...
    in_flight.insert(step.id.clone());
    let _ = events.send(OrchestratorEvent::StepStarted { step_id: step.id.clone(), agent: step.agent.clone() });
    futures.push(tokio::spawn(async move {
        let outcome = run_step_with_retry(&step_clone, &step_inputs, worker, &policy, &events).await;
        (step_clone.id, outcome)
    }));
}

Every ready step gets its own tokio::spawn. FuturesUnordered awaits whichever task completes first — no ordering between parallel siblings.

Two invariants, one predicate:
  • s2/s3 don't start until s1 ∈ completed
  • s4 doesn't start until both s2 AND s3 ∈ completed
Both fall out of the same .all(|d| completed.contains(d)) check in ready_steps.

7 · Replan (step exhaustion)

What happens when the planner emits a valid-shape plan but with a broken detail — e.g. inventing an agent name that's not in the roster.

Real eval trace

T+0.3s step_failed s1 attempt=2 err=(same) T+0.4s step_failed s1 attempt=3 err=(same) T+0.5s step_exhausted s1 T+0.5s replan_triggered step s1: agent "analyst" has no `[agents.analyst]` block ... T+3.2s plan_created steps=[s1:researcher(deps=[]), ...] ← repaired ... continues normally

Core logic

// orchestrator/replan.rs
ExecResult::NeedsReplan { failed, error } => {
    if replans_left == 0 { /* bail with graceful failure message */ }
    replans_left -= 1;
    events.emit(ReplanTriggered { reason: error.clone() });
    plan = planner.replan(user_msg, plan, failed, error).await?;
}

Bounded by OrchestratorConfig.max_replans (default 2). Unknown agents fail fast in runner.rs::run_step (no child spawned); the planner only sees [agents.*] blocks with a description (shared_files::routable_agents). plan.rs::validate is topology-only and exercised by unit tests, not the runtime path. skills/orchestrator/SKILL.md forbids inventing agent names, so this trace rarely triggers — kept as the canonical tier-2 recovery example.

Usage examples

# Validate it still works (default retention, keep last 10)
./target/release/tengu eval orchestration-e2e

# Iterate on a single row without polluting the repo
./target/release/tengu eval orchestration-e2e --filter parallel_fan_out --no-persist

# Keep only the last 3 runs (aggressive retention)
./target/release/tengu eval orchestration-e2e --keep-runs 3

# Keep everything (effectively disable retention)
./target/release/tengu eval orchestration-e2e --keep-runs 9999
