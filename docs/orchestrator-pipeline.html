Tengu Orchestrator — Pipeline

Harness-owned orchestration, parallel + sequential execution, retention. Every diagram references exact file:line locations in the source tree.

1 · Overview

A user message arrives on a channel (Telegram / TUI / Eval runner). The channel calls Orchestrator::handle(prompt). An orchestrator agent emits a JSON plan; a Rust DAG executor dispatches each step as a worker LLM turn; results flow back as a single final response. No LLM ever sees the orchestration machinery directly.

The three execution patterns on this page:

PatternDAG shapeTested by
Sequentials1 → s2eval row two_step_sequential
Parallel + synthesize(s1, s2, ..., sN) → sMeval row parallel_fan_out
Diamond / mixeds1 → (s2, s3) → s4eval row diamond_dag

Prompt

Observed timeline

T+0.0s orchestrator:plan_created steps=[s1:researcher(deps=[]), s2:writer(deps=[s1])] T+0.1s orchestrator:step_started s1:researcher T+0.1s http_request GET .../Status/200 T+1.4s http_request GET .../Status/404 T+14.2s orchestrator:step_succeeded s1 ← executor enqueues s2 only now T+14.3s orchestrator:step_started s2:writer T+22.8s orchestrator:step_succeeded s2 T+22.9s orchestrator:plan_completed cancelled=false
Invariant: s2.depends_on = [s1], so ready_steps at plan.rs:94 returns [s1] first, then [s2] only after s1 is in completed. The 0.1s gap between s1 succeeded and s2 started is the guarantee.

Core logic

// orchestrator/plan.rs:94
pub fn ready_steps(&self, completed: &HashSet<StepId>) -> Vec<&Step> {
    self.steps.iter().filter(|s|
        !completed.contains(&s.id)
        && s.depends_on.iter().all(|d| completed.contains(d))
    ).collect()
}

depends_on.iter().all(|d| completed.contains(d)) is the ONLY code that decides sequential vs parallel. Everything else falls out from it.

Observed timeline — interleaving as proof of concurrency

T+0.0s orchestrator:plan_created (5 steps) T+0.1s orchestrator:step_started s1 ┐ T+0.1s orchestrator:step_started s2 │ all four start T+0.1s orchestrator:step_started s3 │ within ~100ms T+0.1s orchestrator:step_started s4 ┘ T+0.2s http_request (s3) ← interleaved, proof of tokio::spawn T+0.3s http_request (s1) T+0.3s http_request (s4) T+0.4s http_request (s2) ... Invariant: interleaved tool calls prove concurrent execution. If one researcher were doing all four sequentially, tool calls would be grouped by step (all of s1's, then all of s2's). The interleaving is only possible because tokio::spawn ran the four researchers on independent tasks.

Core logic

// orchestrator/executor.rs — inside the main loop
for step in ready {
    if !in_flight.contains(&step.id) {
        in_flight.insert(step.id.clone());
        futures.push(tokio::spawn(async move {
            let outcome = run_step_with_retry(&step_clone, &step_inputs, worker, &policy, &events).await;
            (step_clone.id, outcome)
        }));
    }
}

Every ready step gets its own tokio::spawn. FuturesUnordered awaits whichever task completes first — no ordering between parallel siblings.

Observed timeline

T+0.0s plan_created s1 → (s2, s3) → s4 T+0.1s step_started s1 (s2 and s3 NOT yet started — waiting for s1) T+6.3s step_succeeded s1 ← releases s2 AND s3 T+6.4s step_started s2 ┐ parallel fan-out T+6.4s step_started s3 ┘ after s1 complete T+14.1s step_succeeded s2 T+14.9s step_succeeded s3 T+15.0s step_started s4 ← waits for BOTH s2 and s3 T+20.2s step_succeeded s4 T+20.3s plan_completed
Two invariants, one predicate:
  • s2/s3 don't start until s1 ∈ completed
  • s4 doesn't start until both s2 AND s3 ∈ completed
Both fall out of the same .all(|d| completed.contains(d)) check in ready_steps.

7 · Replan (step exhaustion)

What happens when the planner emits a valid-shape plan but with a broken detail — e.g. inventing an agent name that's not in the roster.

Real eval trace

T+0.0s plan_created steps=[s1:analyst(deps=[]), ...] ← "analyst" not in roster T+0.1s step_started s1:analyst T+0.2s step_failed s1 attempt=1 err=unknown agent: analyst T+0.3s step_failed s1 attempt=2 err=unknown agent: analyst T+0.4s step_failed s1 attempt=3 err=unknown agent: analyst T+0.5s step_exhausted s1 T+0.5s replan_triggered unknown agent: analyst T+3.2s plan_created steps=[s1:researcher(deps=[]), ...] ← repaired ... continues normally

Core logic

// orchestrator/replan.rs
ExecResult::NeedsReplan { failed, error } => {
    if replans_left == 0 { /* bail with graceful failure message */ }
    replans_left -= 1;
    events.emit(ReplanTriggered { reason: error.clone() });
    plan = planner.replan(user_msg, plan, failed, error).await?;
}

Bounded by OrchestratorConfig.max_replans (default 2). The orchestrator prompt now explicitly forbids inventing agent names, so this specific scenario rarely triggers in practice — kept here because it's the canonical trace of how the tier-2 recovery works.

Usage examples

# Validate it still works (default retention, keep last 10)
./target/release/tengu eval orchestration-e2e

# Iterate on a single row without polluting the repo
./target/release/tengu eval orchestration-e2e --filter parallel_fan_out --no-persist

# Keep only the last 3 runs (aggressive retention)
./target/release/tengu eval orchestration-e2e --keep-runs 3

# Keep everything (effectively disable retention)
./target/release/tengu eval orchestration-e2e --keep-runs 9999
