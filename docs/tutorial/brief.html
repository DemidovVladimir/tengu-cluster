Brief: a searcher reads first

Before an agent's turn, its searcher, another agent, reads the request and answers with what the user's knowledge base says, or NONE. A finding leads the request, so the main agent need not search.

  • searcher timeout 60 s by default
  • NONE or empty = no brief
  • A2A agent turns + plan steps
  • 1 level: a searcher has no brief
  • 心 heart searcher and agent
  • 手 hands knowledge base tools
  • 守 guard the answer check
  • data config, brief, history

    Five endings
    
How a brief ends

  

  
    
    
  • briefa findingThe trimmed answer leads the request in the marked block. Log: brief: the searcher's finding leads the request.
    • 
    
  • noneNONE or emptyThe request goes on as it was. Log: brief: the searcher found nothing; no brief.
    • 
    
  • warnthe searcher failedLogged with the error; the request goes on as it was.
    • 
    
  • warnpast timeout_secsThe searcher's turn is dropped; the request goes on as it was.
    • 
    
  • offno brief blockNo searcher turn at all.
    • 
  






  

    Surfaces
    
Where it runs today

  

  
    
    
  • onA2A agent turns/a2a/agents/<a> on tengu a2a serve. The searcher runs in the server process.
    • 
    
  • onplan stepsEvery tengu run-agent child, including the steps the A2A planner dispatches. The searcher runs inside the child, as an in-process agent turn.
    • 
    
  • offthe planner callA turn with a system override (system_override) is never briefed.
    • 
    
  • not yetchat and webhook turnsA turn answered in process on the TUI, Telegram or a webhook gets no brief yet. The plan steps such a turn starts do: each is a tengu run-agent child.
    • 
  






  

    Enforced in code
    
Guarantees

  

  
    
    
  • A brief never fails a turn. A searcher error or a run past timeout_secs logs a warning, and the request goes on unchanged.
    • 
    
  • Bounded in time. The whole searcher turn, tool calls included, is cut at timeout_secs: 60 by default, and 0 is refused.
    • 
    
  • One level deep. An agent may not be its own searcher, and a searcher may not have a brief of its own, so briefs never chain or loop.
    • 
    
  • A real agent. searcher is required and must name an [agents.<name>] block, or the config does not load. Unknown keys in the block do not parse.
    • 
    
  • The request alone. The searcher gets the request text with no conversation history.
    • 
    
  • History stays clean. An A2A context records the request without its brief; only the current turn carries it.
    • 
    
  • Told apart from asked. The brief sits between [Brief from agent `<searcher>`: what the user's knowledge base says that matters for this request] and [End of brief], then a blank line, then the request.
    • 
  






  

    Try it
    
Set one up, then run the tests

    
An example block: the agent names, model and vault path are examples; the tool names come from a chaos-kb [[mcp_servers]] entry named chaos_kb.

  


# example: a researcher briefed by a small knowledge base searcher
[[mcp_servers]]
name      = "chaos_kb"
transport = "stdio"
command   = ["chaos-kb", "--vault", "${HOME}/notes", "mcp"]

# the rest of [agents.researcher] as before
[agents.researcher.brief]
# required: another [agents.<name>] block
searcher     = "kb_searcher"
# the default; must be greater than 0
timeout_secs = 60

# the searcher needs no description
[agents.kb_searcher]
engine = "openrouter"
model  = "<a small, fast model>"
tools  = ["chaos_kb__kb_topics", "chaos_kb__kb_read"]

[agents.kb_searcher.identity]
instructions = """Call kb_topics with the request. kb_read only the ids that would change the
task for this user. Answer those facts in short lines, each with its id, or exactly NONE."""
