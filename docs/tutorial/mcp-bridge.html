MCP bridge

Claude Code runs its own tool loop. Tengu gives it exactly one MCP server, tengu mcp-bridge, which runs Tengu's tools as the calling agent: same scopes, same redaction, same egress. The Codex CLI (engine = "codex") gets the same bridge, registered with -c mcp_servers.tengu-tools.*; its env reaches the bridge by name only (env_vars).

  • tools seen as mcp__tengu-tools__<name>
  • result ≤ 50 000 chars
  • call id mcp:<nonce>:<id>
  • JSON-RPC 2.0 on stdio · 2024-11-05

The env contract

The file the engine writes for one CLI run. Keys come out sorted. Values in angle brackets are placeholders; secrets reach the bridge only by inheritance.


    
The CLI merges this env over its own inherited env, so OPENROUTER_API_KEY, vault values and $VARs for [[mcp_servers]] arrive without being written down.

Four JSON-RPC exchanges

    
One request per line on stdin, one response per line on stdout. Example values; a failed tool is still a result, with isError: true.

    Enforced in code
    
Guarantees

  

  
    
    
  • Same tools, same rules. The bridge registers the same catalog and resolves scopes with the same function as the in-process executor.
    • 
    
  • Only listed tools. Registration keeps only TENGU_BRIDGE_TOOLS; a call to any other name gets the agent's real tool list back.
    • 
    
  • Inside the generation. In a sandbox with [generation], a tool outside it is neither listed by tools/list nor registered, as in-process (Lineage and generations).
    • 
    
  • Nothing secret leaves. Text and typed rows go through SanitizedToolExecutor; errors are redacted in the call handler.
    • 
    
  • Bounded results. At most TENGU_BRIDGE_MAX_RESULT_CHARS (default 50 000) plus a [truncated — showing …] footer.
    • 
    
  • No replayed orders. A fresh nonce per bridge process: two sessions with the same JSON-RPC ids place two orders (tested).
    • 
    
  • The parent's egress. The bridge installs TENGU_EGRESS from the engine, so proxied MCP calls follow the same policy.
    • 
    
  • Proven equal. tests/bridge_conformance.rs runs every catalog tool in-process and through a real bridge, then compares text, files and upstream requests.
    • 
  






  

    Try it
    
Talk to the bridge by hand

    
Without TENGU_BRIDGE_AGENT it falls back to main and says so on stderr; stdout stays pure JSON-RPC. The listing is an example.

  

  


$ export TENGU_BRIDGE_TOOLS='[{"name":"list_directory","description":"List a directory","parameters":{"type":"object","properties":{"path":{"type":"string"}}}}]'
$ printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize"}' '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"list_directory","arguments":{"path":"."}}}' | tengu mcp-bridge 2>/dev/null
{"jsonrpc":"2.0","id":1,"result":{"capabilities":{"tools":{}},"protocolVersion":"2024-11-05","serverInfo":{"name":"tengu-tools","version":"0.1.0"}}}
{"jsonrpc":"2.0","id":2,"result":{"content":[{"text":"notes.txt\nreport.md","type":"text"}],"isError":false}}
$ tengu tool call --agent main --tool list_directory --args '{"path":"."}'
{"is_error":false,"observation":null,"text":"notes.txt\nreport.md"}

  

  
The last command is the in-process twin the conformance test compares against. Same text, same flags.
