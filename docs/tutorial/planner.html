How the reply is parsed

This runs the same four paths as parse_verdict. Pick a sample or type your own.

  1. 1raw JSON
  2. 2strip ```json fences
  3. 3first balanced { } in the text
  4. 4any other text → direct
  5. ✗empty → the turn fails

    
One parse, no retry: SKILL.md says so, and plan_schema.json only documents the shape. A plan step with an unknown agent fails later, at the runner; one whose depends_on names a missing step replans.

    Event bus
    
What the TUI shows during a turn

    
One broadcast channel (capacity 256) per orchestrator. The TUI prints the first seven as orch: system bubbles.

  

  
    
    
  • planPlanCreatedorch: plan created (1 step). Also after every replan.
    • 
    
  • startStepStartedorch: ▶ s1 [crypto_researcher]
    • 
    
  • okStepSucceededorch: ✓ s1
    • 
    
  • failStepFailedorch: ✗ s1 (attempt 1): the error. One per failed attempt.
    • 
    
  • outStepExhaustedorch: ⊘ s1 exhausted: the last error.
    • 
    
  • againReplanTriggeredorch: ↻ replan — the error.
    • 
    
  • endPlanCompletedorch: plan completed. Every path ends with one.
    • 
    
  • opt-inRagQueried · MetricsRecordedShown with TENGU_TUI_RAG_DEBUG=1 / TENGU_TUI_METRICS=1.
    • 
  






  

    Enforced in code
    
Guarantees

  

  
    
    
  • The planner cannot call tools. With a system-prompt override the turn gets an empty tool list, no executor and no memory recall.
    • 
    
  • Only one engine. [orchestrator] engine other than "rag" fails the config load.
    • 
    
  • Private agents stay private. A block without a description never appears in the registry.
    • 
    
  • Memory trouble never blocks a turn. A Postgres or embedding error leaves its block empty and the call goes on.
    • 
    
  • No self-recall. Earlier messages are read before this message is stored.
    • 
    
  • Plans stay per session. Each plan is keyed by its session id; clearing removes only the copy that turn stored.
    •
