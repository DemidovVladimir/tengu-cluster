Sealed keys

No provider key sits on this machine. Each one is sealed to a Cloudflare Worker that alone can open it; tengu sends the sealed blob with the request, and the Worker adds the key and forwards.

  • seal HPKE X25519 · ChaCha20-Poly1305
  • session 24 h (1–168 per key)
  • revoke ≤ 60 s
  • secret ≤ 4096 bytes
  • 守 guard Secure Enclave, Worker checks
  • 手 hands the upstream API
  • data blobs, vault key, allow-list

Worker answers

What can come back

  • 200forwardedThe upstream's own answer, streamed back unchanged.
  • 401not allow-listed, expired or forgedNo clients:<fp>, a session past its expiry, or one from another Worker key.
  • 403refusedA tampered blob, a kid mismatch (reseal), a client not in the blob's list, or a path that leaves the upstream.
  • 400malformedNo blob, an unknown route, a bad session request.
Enforced in code

Guarantees

  • Only the Worker can open a blob. HPKE to the Durable Object's key; the metadata is the AAD, so changing the upstream breaks the seal.
  • The key goes only where it was sealed for. The target is built from the sealed upstream and re-parsed: same scheme, host, port, and a path inside the base path.
  • No session without the agent key. Every session needs a fresh signature by an allow-listed key; a signature for another Worker origin fails.
  • The session goes only to the proxy. auth_header_for and header_mode return nothing for any other origin.
  • Never on disk. The session lives in process env; its name ends in _TOKEN, so every redaction registry built after it masks it.
  • No redirect follow. The Worker fetches with redirect: manual.
  • Quiet logs. One line per request: route, client label, upstream host, status, ms. Never headers, bodies or secrets.

Not a sandbox. While tengu runs, an agent with a shell on the same machine can use the session or the agent socket too. What it cannot do is read a provider key: there is none here.
