Skill evals and evolution

tengu eval replays a skill's prompts through a live agent and an LLM judge. tengu skill evolve rewrites a failing skill in a scratch worktree, scores it again, and changes nothing until you say yes.

A run's pass rate = passing rows ÷ rows for that metric. stddev needs two runs in the window. Old metrics/runs/<ts>/ folders beyond 10 are pruned.

  






  

    Declared in SKILL.md frontmatter
    
Six metric kinds

    
At load, names must be unique, min_pass_rate in [0, 1] and named files present, or the run stops. A metric that errors while scoring is a fail with a note.

  

  

    
llm_judge
rubric_file
The judge reads the rubric, prompt, transcript and expected outcome; its verdict is the metric's result for that row.

    
description_trigger
queries_file · runs_per_query 3 · holdout 0.4
Would the planner pick this skill? Strict majority of 3 votes per held-out query; passes at min_pass_rate, else 0.85.

    
shell_check
cmd · expect_exit_code · expect_stdout_matches
Runs a command. Needs at least one expectation; exit 0 is required even when only a regex is set.

    
script
path → stdout {pass, score, notes}
Runs sh <path> with the row's PROMPT, TRANSCRIPT and EXPECTED_OUTCOME in its env.

    
tool_assertion
tool · action · key · assert
Calls a registered tool and checks its output. tengu eval runs it through the agent's tool executor, in the agent's workspace.

    
dialog_replay
from_message_index · delegate_metric
Scores the live conversation slice through a sibling llm_judge or tool_assertion. Eval rows have no conversation: fail.

  






  

    In chat: opt-in tools
    
Distill and improve from a conversation

    
Both are opt-in names in an agent's tools or workspace_tools. Neither loads the change into the current conversation.

  

  

    

      
skill_distill

      
Turns the conversation from from_message_index into a new skill: SKILL.md with metrics, fixtures extracted from the transcript, a seeded evals/config.toml, rubric and script stubs.

      
  • name ^[a-z][a-z0-9-]{1,63}$, unused in every tier
  • tier project or workspace; managed refused
  • no conversation passed → refused, nothing written

    

    

      
apply_improver_proposal

      
The in-chat twin of the evolve apply step: new body, optional metrics, resource_additions, a rationale. Atomic writes, one audit line.

      
  • refused on editable_by_learner: false
  • resource paths stay inside resources/
  • an existing resource needs overwrite: true

    

  

  
The same plugin family also serves compress_and_store, the step-summary protocol of Subagent steps.

    How an evolve run ends
    
Six endings

  

  
    
    
  • yacceptedSKILL.md and resources written, re-scored, worktree removed.
    • 
    
  • nrejectedNothing changed; worktree removed.
    • 
    
  • ddetails-then-discardRationale, rollups and metrics printed as JSON; nothing changed.
    • 
    
  • oopen worktreePath printed and kept for you; nothing logged.
    • 
    
  • flagrefused-by-flagYou said y, but editable_by_learner: false.
    • 
    
  • noneno winnerNo cycle beat the target's baseline without another metric dropping by more than 0.05. No gate; worktree kept.
    • 
  






  

    Enforced in code
    
Guarantees

  

  
    
    
  • No change without you. Evolve writes the real SKILL.md only after y at the terminal gate; any other answer leaves it as it was.
    • 
    
  • Cycles are isolated. Proposals are applied and scored in a git worktree .tengu/worktrees/evolve-<skill>-<ts> (outside git: a copy in .tengu/scratch/); worktrees older than 24 h are swept at the next start.
    • 
    
  • Locked skills stay locked. editable_by_learner: false stops evolve's apply, apply_improver_proposal and manage_skill edits.
    • 
    
  • Evals stay contained. Each row gets a fresh temp folder; tool output is redacted; stubs never reach a claude_code agent's bridge (that row is refused).
    • 
    
  • A timeout is a fail. A row past its timeout_secs fails without a judge call; malformed judge output fails with a preview.
    • 
    
  • Installs are checked first. Symlink escapes are rejected; --strict refuses a caution or dangerous verdict; an existing target is never overwritten.
    • 
    
  • Busy skills can't vanish. remove and manage_skill delete refuse while an evolve worktree for that skill exists.
    •
