Agents

An agent is a TOML file describing a subprocess: which model, which tools, which skills, how long to run. Drop a file under agents/ and restart chat — auto-reindex picks it up.

1Schema

FieldTypeNotes
namestring, requiredMust match filename stem. Plans reference this exact value.
descriptionstring, requiredThis is what the RAG registry embeds. Write it for semantic search — what it handles, what it is NOT.
example_queriesarray<string>Each entry indexed as a SECOND vector. Short user phrasings ↔ short examples win over long descriptions. Highly recommended.
enginestring, default "openrouter"Or "claude_code". Don't use claude_code for the planner agent.
modelstring, requiredOpenRouter slug ("anthropic/claude-sonnet-4-6") or bare Claude name ("claude-sonnet-4-6").
toolsarray<string>Tool allow-list. compress_and_store is appended implicitly — don't list it.
skillsarray<string>Skill names. Resolved through the three-tier scanner.
max_turnsu32, default 20Cap on subagent's mini-loop.
timeout_secsu64Hard subprocess timeout.
sandboxpath, optionalPersistent workspace dir. If absent, runner creates a temp dir.

2Minimum-viable example

Drop this at agents/btc-watcher.toml:

name = "btc-watcher"

description = """
Looks up live cryptocurrency prices via public APIs. \
Best for: 'what is the BTC/ETH/SOL price right now', 'price of '. \
NOT for: trading, analysis, or anything that needs a wallet.
"""

example_queries = [
    "what is the BTC price?",
    "price of ETH right now",
    "current SOL price in USD",
]

engine = "openrouter"
model = "anthropic/claude-sonnet-4-6"
tools = ["http_request"]
skills = []
max_turns = 6
timeout_secs = 60

3Verify it landed

# the planner registry is regenerated on the next planner turn — restart the TUI, then:
rg -n btc-watcher TENGU_PLANNER_REGISTRY.md

# durable memory writes: query Postgres agentic_memory via TENGU_MEMORY_DATABASE_URL
psql "$TENGU_MEMORY_DATABASE_URL" -c "select kind, left(content, 80) from agentic_memory order by created_at desc limit 10"
Gotcha — the orchestrator agent (e.g. aura) is BOTH planner and a routable subagent. The planner role strips tools/memory; when dispatched as a subagent, the subprocess gets the full tools/skills list back. Same TOML, two roles.
Gotcha — workspace_tools = [...] in agents/*.toml is silently ignored. Put privileged tool names (shared_cache, persistent_store, skill_distill, apply_improver_proposal, manage_skill) in the regular tools array. The harness derives the synthesized workspace_tools by filtering against WORKSPACE_TOOLS_ALLOWLIST.

Skills

A skill is a folder containing a SKILL.md with YAML frontmatter, plus optional resources/ and evals/. The body is loaded into the system prompt of any agent that lists this skill in its skills = [...].

1Three-tier scanner — where to drop your skill

TierPathUse for
1 (managed)~/.tengu/skills/<name>/System-installed skills shared across workspaces.
2 (workspace dotdir)<workspace>/.tengu/skills/<name>/Workspace-private skills; gitignored by convention.
3 (workspace root) — winning tier<workspace>/skills/<name>/Project-canonical skills; tracked in git.

First-match wins (workspace root shadows workspace dotdir shadows managed).

2Anatomy

skills/
  spanish-teacher/
    SKILL.md              # required — frontmatter + body
    resources/            # optional — heavy reference material
      grammar-cheatsheet.md
    evals/                # optional — used by `tengu skill evolve` + metrics
      prompts.yaml
      config.toml

3Frontmatter

FieldRequiredNotes
nameyesLetters, numbers, hyphens. Matches dir name.
descriptionyesStart with "Use when…". Triggering conditions only — never summarise what the skill does.
editable_by_learnernotrue = accepts in-chat 'adjust yourself' / 'fix it' from learning-agent. Default false.
learner_facingnoWhether this skill is visible to the user-facing learner-platform UI.
requires_bins / requires_env / osnoGating — skill is skipped when prerequisites absent.
metricsnoUsed by tengu skill evolve + tengu skill metrics.

4Minimum-viable example

Drop this at skills/spanish-teacher/SKILL.md:

---
name: spanish-teacher
description: Use when the user wants to practice Spanish — translate phrases, check grammar, or hold a beginner conversation in Spanish.
editable_by_learner: true
---

# Spanish Teacher

You teach beginner Spanish. Default to Castilian unless the user specifies LatAm.

## When to Use
- The user asks to practice Spanish
- The user wants a phrase translated
- The user wants grammar feedback in Spanish

## Style
- Reply 50/50 Spanish/English for absolute beginners.
- Switch to mostly-Spanish once the user shows fluency.
- Correct mistakes inline with `**bold**` for the right form.

5Wire it to an agent

Open agents/<name>.toml and add the skill name to skills = [...]. Restart chat. The skill body becomes part of that agent's system prompt at runtime.

6Verify

./target/release/tengu skill list                    # all installed skills, by tier
./target/release/tengu skill doctor                  # informational scan over installed skills

# confirm the planner sees it (file regenerated on the next planner turn)
rg -n "practice Spanish" TENGU_PLANNER_REGISTRY.md
Gotcha — when only a SKILL matches your query (no agent matches), the planner CAN'T put a skill name in a plan step. Skills are reference material loaded by an agent. The orchestrator SKILL.md tells the planner: route to the closest agent and let it consult the skill via its skill loader.
Gotcha — skills/orchestrator/SKILL.md is special: it's the planner system prompt. Don't load it on a non-planner agent. editable_by_learner: false on this skill — harness-critical, locked.

Tools

A tool is a Rust plugin module that an agent's LLM can call by name. Built-in tools live in src/adapters/plugins/. Adding a new one is a one-line registration.

Built-in tool catalog

ToolPurposePlugin
http_requestHTTP fetch with scope-gated host allow-listplugins/http
read_file / list_directory / run_commandWorkspace primitivesplugins/workspace
get_wallet_address / sign_and_send_transaction / sign_messagePrivy wallet opsplugins/crypto
view_skillAlways-on read API for skillsplugins/view_skill
compress_and_storeSubagent terminal "I'm done"plugins/skill_lifecycle (implicit)

Workspace-tools allow-list

Five privileged names. Opt in by listing them in an agent's tools array:

shared_cacheCross-agent KV cache
persistent_storeDurable per-agent KV
skill_distillBuild a skill scaffold from a successful conversation
apply_improver_proposalApply a JSON proposal from tengu skill evolve
manage_skillAtomic create/edit/patch/add_resource — used by learning-agent

The constant: channel_runtime::WORKSPACE_TOOLS_ALLOWLIST.

Adding a new tool — Phase 7.7 single-place edit

Pre-7.7 you had to register in two places (the in-process executor and the MCP bridge). Now there's one helper.

// 1. New plugin module: src/adapters/plugins/btc_price/mod.rs
//    Exports tool_defs() returning Vec<ToolDef> and a Plugin impl.

// 2. ONE line in src/adapters/channel_runtime.rs::register_core_plugins:
fn register_core_plugins(registry: &mut ToolRegistry, ...) {
    registry.register(HttpPlugin::new(...));
    registry.register(WorkspacePlugin::new(...));
    registry.register(BtcPricePlugin::new(...));   // ← add here
    // ...
}

// 3. List the tool in your agent:
//    agents/btc-watcher.toml
//    tools = ["http_request", "btc_price"]

MCP bridge — exposing tengu tools to Claude Code subagents

When a subagent has engine = "claude_code", the harness spawns tengu mcp-bridge as an MCP server for the Claude Code CLI. Tools surface to Claude as mcp__tengu-tools__<name>. Same registration helper — both call paths converge.

Gotcha — Claude Code replaces inherited env when launching MCP servers, so two env vars MUST be forwarded explicitly: TENGU_SESSION_ID (for compress_and_store writes to land in the right session) and OPENROUTER_API_KEY (for the embedder + memory tools).

Tool scopes

Each tool that touches the network or env reads is scoped per-agent or by sandbox default:

# sandboxes/aura/config.toml
[default_scopes.http_request]
net_hosts = ["*"]                # "*" = wildcard (dev only)
env_reads = ["*"]

# Per-agent override (wholesale, NOT field-merged):
[agents.aura.scopes.http_request]
net_hosts = ["api.coingecko.com", "api.privy.io"]
env_reads = ["PRIVY_APP_ID", "PRIVY_APP_SECRET"]

Sandboxes

A sandbox is a TOML config bundling a deployment: which orchestrator agent runs, what scopes apply, what secrets are available, what MCP servers connect, what the workspace scaffold looks like.

1Where it lives

sandboxes/<name>/config.toml. Reference at launch:

tengu chat     --sandbox aura
tengu telegram --sandbox aura

2Sections

SectionPurpose
runtime_profile"cloud" or "local" — affects engine defaults.
[orchestrator]agent (planner agent name), engine = "rag" (the only valid value), max_attempts_per_step, max_replans.
[memory]Memory subsystem on/off + cross-session knobs (cross_session_msg_top_k, etc.).
[telegram]allowed_users, tool_approvals, approve_only.
[claude_code]cli_path, timeout_secs for Claude Code engine.
[default_scopes.<tool>]Fallback scopes when an agent has none of its own.
[scaffold]Root workspace path + directories created on startup.
[skill_lifecycle]improver_agent, fixture_runner_agent, evolution caps.
[agents.<name>]Per-deployment overrides — workspace, default flag, lifecycle agents (skill-improver, fixture-runner).
[mcp.<name>]MCP servers to mount (URL, transport, auth).

3Minimum-viable sandbox

# sandboxes/hello/config.toml
runtime_profile = "cloud"

[orchestrator]
agent = "aura"
engine = "rag"
max_attempts_per_step = 3
max_replans = 2

[memory]
enabled = true

[default_scopes.http_request]
net_hosts = ["*"]
env_reads = ["*"]

[scaffold]
root = "~/hello-workspace"
directories = ["research"]

4Verify

# Lints config + checks API keys
./target/release/tengu doctor

# Pretty-print resolved config
./target/release/tengu status
Gotcha (Phase 7.2) — Config.sandbox_name is #[serde(skip)], populated by load_sandbox_or, threaded through SubprocessRunner → AgentIpcInput.sandbox_config. Without this, child subprocesses load ~/.tengu/config.toml not the parent's sandbox config — http_request scope-denies in the child even when the parent's sandbox allows it.
Gotcha — engine = "rag" is the only valid orchestrator engine post-7.1. Anything else logs warn and disables orchestration for that channel. Run with tengu chat --sandbox <name>.

Webhooks (inbound HTTP)

External systems POST to /webhooks/<name>; tengu HMAC-verifies the request and dispatches a one-shot orchestrator turn. Each endpoint is a TOML block — adding a new webhook is a config edit, no recompile.

1Build with the feature on

cargo build --release --features "postgres_memory claude_code webhooks"

2Add an endpoint to the sandbox config

# sandboxes/aura/config.toml

[webhooks]
enabled = true
bind = "127.0.0.1"   # 0.0.0.0 to expose externally
port = 7080

[webhooks.endpoints.github_pr]
agent = "reviewer"
secret_env = "GITHUB_WEBHOOK_SECRET"   # name of env var holding the shared secret
goal_template = "A GitHub PR webhook arrived. Review and post a summary."

[webhooks.endpoints.local_test]
agent = "aura"
secret = "literal-dev-secret"          # inline (dev only — env var preferred)

3Run the listener

GITHUB_WEBHOOK_SECRET="abc123" \
  RUST_LOG=tengu=info \
  ./target/release/tengu webhooks --sandbox aura
# tengu webhooks listening bind=127.0.0.1 port=7080 endpoints=["github_pr","local_test"]

4Send a signed POST

BODY='{"action":"opened","pr":{"number":42}}'
SIG=$(echo -n "$BODY" | openssl dgst -sha256 -hmac "abc123" | awk '{print $2}')
curl -X POST http://127.0.0.1:7080/webhooks/github_pr \
  -H "X-Tengu-Signature: sha256=$SIG" \
  -H "Content-Type: application/json" \
  -d "$BODY"
# 202 Accepted
# {"status":"accepted","session_id":"webhook-github_pr-...","endpoint":"github_pr","agent":"reviewer"}

5Verify the agent ran

# Replace with the session_id from the curl response — query Postgres agentic_memory via TENGU_MEMORY_DATABASE_URL
psql "$TENGU_MEMORY_DATABASE_URL" -c "select kind, step_id, left(content, 80) from agentic_memory where session_id = 'webhook-github_pr-<uuid>'"
# Each compress_and_store row from the agent's run shows up here.

HMAC signature shape

FieldValue
Header nameX-Tengu-Signature
Formatsha256=<lowercase-hex>
AlgorithmHMAC-SHA256(body, secret)
Compareconstant-time via hmac::Mac::verify_slice
On mismatch401 Unauthorized

Response shape

StatusWhenBody
202 AcceptedHMAC verified, dispatch spawned{"status":"accepted","session_id":"…","endpoint":"…","agent":"…"}
404 Not FoundUnknown endpoint name{"error":"…"}
401 UnauthorizedMissing / malformed / mismatched signature{"error":"…"}
500 Internal Errorsecret_env points at unset variable{"error":"server misconfiguration: …"}
Async-only in v1 — the listener returns 202 immediately and the agent runs in the background. There's no way to wait for the agent's reply over HTTP. Use the returned session_id to retrieve the result asynchronously — query Postgres agentic_memory via TENGU_MEMORY_DATABASE_URL.
Persistence (Fix H · 2026-05-09) — every webhook turn's final text is written to Postgres agentic_memory with synthetic step_id = "webhook-handler". This guarantees a query of agentic_memory via TENGU_MEMORY_DATABASE_URL returns at least one row even when the planner answered directly without dispatching a subagent. Subagent compress_and_store rows (when they fire) coexist with separate step_ids.
Per-request orchestrator — each webhook request constructs a fresh orchestrator. The Postgres pool lazy-inits on first plan(), so the first hit takes longer for the connection handshake. Tolerable for low rates; if your webhook traffic climbs, share the pool across requests (open follow-up).
Default-deny exposure — defaults bind to 127.0.0.1. Change to 0.0.0.0 only after configuring HMAC. Don't leave inline secret = "..." in a TOML committed to a public repo — use secret_env with a secrets-manager-loaded env var.
Compile-time gate — webhooks are off by default. Without --features webhooks, the tengu webhooks command prints "webhook listener requires: cargo build --features webhooks" and exits.
