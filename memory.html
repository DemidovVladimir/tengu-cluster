Unified session_id (Fix B · 2026-05-09)

Resolved as of 2026-05-09. channel_runtime::build_orchestrator resolves the id ONCE — env override TENGU_SESSION_ID > fresh UUID — and passes the same string to both RagPlanner::new(...) and SubprocessRunner::new(sandbox_name, session_id). The IPC payload's session_id matches the planner's, so compress_and_store writes extra.rag_session_id equal to the planner's id, and the planner can filter retrieval to the current session.

Pre-Fix-B these were minted independently — the long-standing open issue from the original handoff. SubprocessRunner::default() still mints a fresh UUID for standalone test / CLI use; the unified-id guarantee lives at the build_orchestrator boundary.

Within-session output recall (Fix A · 2026-05-09)

Opt-in via a config knob. Without it, tengu_outputs is only read on replan(), so follow-up questions like "was the molecule project created?" used to come back with "I have no record of that step" — the planner literally couldn't see what its own subagents had done.

# sandboxes/<name>/config.toml
[memory]
enabled = true
within_session_output_top_k = 5    # 0 = off (default)

When > 0, RagPlanner::plan injects a ## Recent step outputs (this session) block from tengu_outputs filtered to the planner's session_id. Pairs with Fix B — the filter only matches because parent and child agree on the id.

Operating the registry

# What's there?
./target/release/tengu registry list --limit 50

# Run the same search the planner runs
./target/release/tengu registry search "your query" --top-k 10

# If Qdrant was reset, the workspace fingerprint will mask an empty store —
# bypass the dedup:
TENGU_REGISTRY_FORCE_REINDEX=1 ./target/release/tengu registry reindex-all

# Wipe + rebuild from scratch
./target/release/tengu registry clear
./target/release/tengu registry reindex-all

Inspecting durable writes (diagnostic · 2026-05-09)

When the planner says "I have no record of that step", run:

# What did this session actually persist?
./target/release/tengu memory inspect --session smoke-2026-05-09 --limit 50

# Same, but for user messages instead of step outputs
./target/release/tengu memory inspect --session smoke-2026-05-09 --collection messages

Output is one row per matching entry — index, step_id, snippet, created_at + age. An empty result prints a checklist (Fix-C not built, Fix-D not built, collection reset, session_id mismatch). Use this BEFORE rerunning a long pipeline — it answers the "is the data even there?" question directly.

Gotcha — .tengu/registry-fingerprint stores a hash of the workspace state. If you reset Qdrant (different container, dropped collection) WITHOUT changing any agent/skill/tool TOML, the auto-reindex will think nothing changed and skip. Force a rebuild with TENGU_REGISTRY_FORCE_REINDEX=1.

Cross-session recall

Off by default. To turn on, set memory.cross_session_msg_top_k in your sandbox config:

# sandboxes/<name>/config.toml
[memory]
enabled = true
cross_session_msg_top_k = 3   # 0 = off (default)

When > 0, the planner runs a semantic search over tengu_messages for prior user questions and injects them as a fenced <memory-context> block. The search runs before persisting the current message, so the just-written message can never appear in its own recall block.

The meta-skill — creating and updating skills in chat

In-chat lifecycle is unified through one agent + two tools: learning-agent + view_skill (read) + manage_skill (atomic write). Replaced 4 specialised agents that were patching JSON proposals at each other.

Lifecycle verbs the orchestrator routes here

VerbPlan
create skill · save this conversation as a skill1-step plan → learning-agent
evaluate · evaluate the <skill> against this session1-step plan → learning-agent
adjust yourself · fix it · improve1-step plan → learning-agent
add a YouTube link to the <skill> resources1-step plan → learning-agent

The agent decides at runtime which view_skill reads, which http_request fetches, and which manage_skill writes to fire — see agents/learning-agent.toml.

manage_skill — six atomic actions

createAtomic write of new SKILL.md + resources/README.md + evals/prompts.yaml stub. Defaults: learner_facing: true, editable_by_learner: true.
edit_bodyFull body rewrite. Frontmatter preserved.
patchFuzzy find-and-replace (v1: exact + whitespace-normalised). 0-match → helpful error with file preview. >1 match without replace_all → ambiguous-match refusal. Refuses breaking-change frontmatter edits.
add_resourceAtomic write under resources/<path>. Path validated. overwrite: false default.
remove_resourceAtomic delete.
deleteRefuses with active scratch worktree (.tengu/worktrees/evolve-<name>-*).

Every write

  • Validates the skill name
  • Refuses on editable_by_learner: false
  • Atomic temp + rename — no half-written files
  • Appends one line to skills/.audit.jsonl
  • Returns {action, skill, ..., loaded_in_current_conversation: false} — the new content activates on next chat session
Cache discipline — skill bodies are loaded into the system prompt at agent construction, not per-turn. After manage_skill writes, the running session keeps using the OLD body until you restart the chat. The harness returns loaded_in_current_conversation: false so the agent can tell the user.

Try it from the chat

tengu chat --sandbox aura

> save this conversation as a skill called bitcoin-faq
[learning-agent fires: view_skill list → manage_skill action="create" → manage_skill action="add_resource" → tells you to restart]

> adjust yourself for the spanish-teacher skill
[learning-agent fires: view_skill read → http_request for fresh material →
 manage_skill action="patch" or action="add_resource"]

> fix it
[same flow scoped to whatever skill the dialog was about]

The offline path — tengu skill evolve

For metric-driven skill rewriting (rescore until it improves), there's a CLI-only path independent of in-chat lifecycle:

tengu skill evolve spanish-teacher --max-cycles 3 --sandbox aura
tengu skill metrics spanish-teacher --last 5

Metrics are stored in skills/<name>/metrics/history.jsonl with rolling pass-rate + stddev + min/max. The improver agent (configured via [skill_lifecycle] improver_agent = "skill-improver") proposes; the harness scores via fixtures; Decision::Apply commits on improvement, refuses on editable_by_learner: false.
