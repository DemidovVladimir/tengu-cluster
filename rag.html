RAG · how Tengu finds the right agent for every message

Three Qdrant collections, one embedder, two query lanes. The "brain" half of the doctrine — RAG = brain, LLM = heart, tools = hands.

Tengu's RAG is not used to ground LLM answers in documents. It's used to route: every user message becomes a vector that's matched against a registry of installed agents, skills, and tools, and the top-K matches become the planner's roster. A second, optional lane recalls prior user messages and prior step outputs for context. The same embedder, three different collections, two different query intents.

Two RAG calls per turn

A user message hits the registry first (always), and optionally the message/output collections for recall.

Lane 1 · Routing (always-on)

Runs on every plan() and replan().

RagPlanner::plan(user_message)
 → search_registry(user_message, top_k=20)
 → format_roster(hits) — three sections
   · ## Available agents
   · ## Available skills (reference only)
   · ## Available tools (reference only)
 → planner LLM emits JSON plan

Lane 2 · Recall (opt-in / on replan)

Three flavors of recall depending on which knob is on. Cross-session is global; within-session filters to the current session_id; cross-plan fires automatically on replan.

// when memory.cross_session_msg_top_k > 0:
search_messages(user_message, top_k)
 → "<memory-context>" block prepended to planner prompt

// when memory.within_session_output_top_k > 0:    [Fix A · 2026-05-09]

                           planner.session_id, top_k)
 → "## Recent step outputs (this session)" block

// on replan path only:

 → "Recall from prior step outputs" block

Operating it

# Inspect what's in tengu_registry
./target/release/tengu registry list --limit 50

# Run the same search the planner runs
./target/release/tengu registry search "your query here" --top-k 10

# Force a fresh reindex (fingerprint dedup will otherwise skip if unchanged)
TENGU_REGISTRY_FORCE_REINDEX=1 ./target/release/tengu registry reindex-all

# Wipe + rebuild from scratch
./target/release/tengu registry clear
./target/release/tengu registry reindex-all

Score interpretation

Realistic agent scores against well-formed user queries fall in 0.15–0.40. A score of 0.6+ is rare and usually indicates a near-verbatim match. The planner SKILL.md hard-rules: do NOT require 0.6 to delegate — the score is a sanity floor, the LLM's reading of the description is the primary signal.

ScoreRead
0.6+Near-verbatim match. Often the user phrased the query exactly like an example_queries entry.
0.4–0.6Strong match. Route confidently if the description fits.
0.2–0.4Plausible match. Read the description; route if it fits, ask for clarification if not.
0.15–0.2Noise floor. Usually right to ask the user to clarify rather than guess.
< 0.15Below floor — agent does not appear in the roster after dedup.
Common failure mode — Qdrant reset or first-run-with-no-data, but .tengu/registry-fingerprint exists from an earlier run. Auto-reindex skips ("nothing changed") but Qdrant is empty. The planner sees an empty roster and replies "RAG registry appears to be empty." Fix: TENGU_REGISTRY_FORCE_REINDEX=1 tengu registry reindex-all.

What's distinct about Tengu's RAG

  • Per-example vectors. Each example_queries entry on an agent is indexed as its own vector — "what is the BTC price?" matches the example line directly instead of fighting the asymmetry between short user phrasings and long formal descriptions.
  • Three sections in the roster. Hits are grouped into ## Available agents / ## Available skills / ## Available tools. The planner can ONLY put an agent name in a plan step's agent field — skills and tools in the roster are reference material the planner reads while deciding.
  • Workspace fingerprint dedup. Hash of every spec + skill + tool. Auto-reindex skips when the hash matches the cache. Saves ~29 embedding calls per startup.
  • Two recall lanes, one embedder. Same text-embedding-3-small serves routing (registry) and recall (messages, outputs). One model = one cost surface = one rate limit.
  • No content RAG. Tengu does not use RAG to ground generation in documents — that's the agent's job via http_request / file tools. RAG is purely the routing + recall layer.
